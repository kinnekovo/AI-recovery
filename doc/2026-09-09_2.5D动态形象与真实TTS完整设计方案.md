# 2.5D 动态形象与真实 TTS 完整设计方案

日期：2026-09-09

## 一、方案结论

本阶段将现有 Static 2D Avatar 升级为“人脸感知的 2.5D 照片数字人”，并接入真实中文 TTS。

用户上传的素材不再允许是任意图片，而应是一张取得授权的、单人、正面、清晰人物照片。系统在浏览器本地检测人脸并生成少量归一化动画锚点，用这些锚点驱动头像的呼吸、状态动画与唇部运动。真实语音由后端 TTS Provider 生成，前端通过 Web Audio API 分析实际音频能量，驱动说话强度。

本方案的定位是“陪伴式照片数字人”，不是写实视频数字人，也不把音量驱动的嘴部运动宣传为医学级构音示范。

### 当前部署验证状态（2026-09-09）

- 正面照校验、居中裁剪预览、锚点持久化、2.5D 状态动画、鉴权 Blob 播放、音频能量嘴部驱动、缓存与浏览器语音降级均已实现并通过本地构建/测试。
- 腾讯云 TTS 的 SDK、凭据和实际请求链路已验证，但云端返回 `UnsupportedOperation.PkgExhausted`，表示账号语音资源包额度已耗尽。此项不是代码故障：补充或开通资源后即可恢复真实云端语音。
- 在额度恢复前，界面会明确标示“已切换设备语音”，训练和录音流程仍可演示；但“真实云端音频实测通过”不得在答辩材料中声明为已完成。

一期推荐技术路线：

```text
正面人物照片
-> 浏览器本地人脸定位和上传校验
-> 保存原图与少量动画锚点
-> Canvas/CSS 分层渲染 2.5D 动作
-> FastAPI 调用腾讯云真实 TTS
-> 鉴权下载音频 Blob
-> Web Audio API 分析音量
-> 驱动嘴部、头部和状态反馈
```

## 二、目标与非目标

### 2.1 一周答辩版本目标

1. 用户能够上传一张正常正面人物照片，并在提交前看到校验和裁剪预览。
2. 训练入口和训练会话中的人物不再完全静止。
3. 数字人能够使用自然中文语音朗读训练说明和任务示范。
4. 说话动画与实际音频强弱同步，不再随机开合。
5. 开始录音时，数字人立即停止播报，避免污染患者录音。
6. TTS、音频或人脸识别失败时，训练流程仍然可用。
7. 保留当前 Avatar Provider 抽象，为后续 Live2D、3D 或视频数字人升级留出接口。

### 2.2 后续试用目标

1. 增加语音生成缓存、使用量统计和失败率监控。
2. 根据患者反馈调整语速、音色、动作幅度和自动播报策略。
3. 支持治疗师或家属为患者选择更合适的标准音色。
4. 在完成单独授权和供应商评估后，再考虑声音复刻。
5. 若未来需要精确构音示范，接入音素/viseme 时间戳并进行临床校准。

### 2.3 明确不做

- 不使用云端视频数字人。
- 不在本阶段接 Live2D Cubism、Three.js 3D 模型或 GPU 推理服务。
- 不根据一张照片生成写实说话视频。
- 不承诺照片嘴型准确表示汉语音素。
- 不把上传声音样本作为标准 TTS 的必选项。
- 不让数字人替代治疗师作诊断、处方或医学判断。

## 三、用户与使用场景

主要用户是脑卒中后言语障碍患者，使用场景是家庭或康复辅助环境中的短时、重复训练。患者可能存在注意力、操作能力或阅读能力下降，因此数字人动作必须温和、可预测，控制项必须少且清楚。

数字人的职责：

- 说明今天练什么。
- 示范需要朗读或回答的内容。
- 在患者说话时明确表现为倾听状态。
- 在分析等待期间提供稳定反馈。
- 完成任务后给予简短鼓励。

数字人不承担：

- 呈现评分细则。
- 对患者进行诊断。
- 使用夸张动作吸引注意力。
- 在患者录音期间继续发声。

## 四、照片输入规范

### 4.1 上传要求

上传界面明确提示：

> 请上传一张已获得本人授权的正面人物照片。照片中只保留一位人物，面部清晰、无遮挡、光线均匀，建议人物看向镜头。

建议校验条件：

| 项目 | 建议规则 |
| --- | --- |
| 格式 | JPEG、PNG、WebP |
| 文件大小 | 不超过 10 MB |
| 最小尺寸 | 短边不低于 512 px |
| 人数 | 仅检测到 1 张主要人脸 |
| 面部占比 | 人脸宽度约占图片宽度的 25%–70% |
| 姿态 | 接近正面，明显侧脸不通过 |
| 清晰度 | 不接受明显模糊、过暗或过曝 |
| 遮挡 | 口罩、手部或大面积物体遮挡眼口时不通过 |

这些规则服务于动画稳定性，不应宣称是身份识别或医学判断。

### 4.2 本地人脸定位

优先在浏览器内使用 MediaPipe Face Landmarker，只处理上传预览，不把人脸关键点发送给第三方。Face Landmarker 可输出归一化人脸关键点、可选 blendshape 和面部变换矩阵；本项目只保留渲染所需的少量位置数据。

保存的数据不包含人脸特征向量，只包括：

```json
{
  "schema_version": 1,
  "face_box": { "x": 0.22, "y": 0.10, "width": 0.56, "height": 0.68 },
  "left_eye": { "x": 0.39, "y": 0.38, "width": 0.10, "height": 0.04 },
  "right_eye": { "x": 0.61, "y": 0.38, "width": 0.10, "height": 0.04 },
  "mouth": { "x": 0.50, "y": 0.61, "width": 0.18, "height": 0.07 },
  "crop": { "x": 0.12, "y": 0.00, "width": 0.76, "height": 0.95 },
  "quality": "auto",
  "motion_scale": 1.0
}
```

坐标全部相对于原图归一化，避免绑定具体像素尺寸。

### 4.3 校准与失败处理

上传流程应提供一个简单预览：

1. 系统自动把人物居中。
2. 预览播放一次两秒钟的呼吸和说话动作。
3. 用户确认“效果正常”后提交。
4. 若自动定位失败，提示重新上传；答辩版不强制开发复杂的人脸编辑器。

后续试用版可以增加轻量手动校准：移动裁剪框，并拖动眼睛和嘴部锚点。手动校准不修改原图，只修改归一化布局数据。

## 五、2.5D 视觉引擎设计

### 5.1 渲染原则

2.5D 的含义不是生成新视频，而是把同一张正面照片分成若干视觉层进行小幅运动：

```text
环境光环层
  └─ 背景/卡片层
      └─ 原始照片底层
          └─ 头部裁剪层
              ├─ 左眼局部层
              ├─ 右眼局部层
              └─ 下半脸/嘴部局部层
                  └─ 状态与音量反馈层
```

不生成新的人脸纹理，不替换人物五官，不夸大面部形变。局部层仍然引用用户原始照片，通过裁剪、缩放、位移和遮罩制造轻微运动。

### 5.2 动画能力

| 能力 | 实现 | 建议幅度 |
| --- | --- | --- |
| 呼吸 | 整体缓慢缩放与垂直位移 | 1%–1.8%，周期 3.5–5 秒 |
| 头部存在感 | 头部裁剪层轻微旋转和位移 | 旋转不超过 1° |
| 眨眼 | 眼部裁剪层短时纵向压缩 | 120–180 ms，随机间隔 3–7 秒 |
| 说话 | 下半脸局部层随音量轻微位移/缩放 | 连续平滑，不做随机开关 |
| 倾听 | 降低人物运动，显示柔和输入波纹 | 不播放声音 |
| 思考 | 减弱呼吸，状态光缓慢流动 | 避免旋转加载器压迫感 |
| 鼓励 | 一次轻微点头或上浮后复位 | 400–650 ms |
| 错误 | 停止面部动画，保留静态人物和重试提示 | 不使用抖动动画 |

### 5.3 嘴部同步

一期口型使用 Web Audio API `AnalyserNode`：

1. 获取音频的时域采样。
2. 计算一帧内的 RMS 或平均绝对振幅。
3. 进行噪声门、增益和指数平滑。
4. 把结果归一化到 `mouthEnergy: 0–1`。
5. 用 `mouthEnergy` 控制下半脸层的纵向位移、缩放和阴影强度。

推荐处理：

```text
原始振幅
-> 噪声门 0.02
-> 增益 2.0–3.0
-> 限制到 0–1
-> attack 约 60 ms
-> release 约 140 ms
-> requestAnimationFrame 更新
```

口型只表达“正在发声和发声强度”，不表达精确音素。训练页面需要避免“看嘴型跟读”等可能造成误解的文案。

### 5.4 自然度控制

- 所有动作都应小幅、低频、非循环机械重复。
- 说话时以声音为主，动画只提供生命感。
- 不在同一时刻叠加眨眼、点头和大幅缩放。
- 长文本每 8–15 秒允许出现一次非常轻微的姿态变化。
- `prefers-reduced-motion: reduce` 下禁用头部视差、点头和上浮，只保留状态颜色与必要的嘴部提示。
- 人脸锚点质量低时自动降级为整图呼吸 + 音量光环，不启用局部面部形变。

## 六、Avatar Runtime 状态机

现有状态保留，但增加明确的进入、退出和打断规则。

| 状态 | 进入条件 | 视觉 | 音频 | 退出条件 |
| --- | --- | --- | --- | --- |
| `idle` | 页面就绪或播报结束 | 呼吸、偶尔眨眼 | 无 | 播报、录音或分析开始 |
| `loading_speech` | 正在请求或下载 TTS | 轻微呼吸、准备提示 | 无 | 音频就绪或失败 |
| `speaking` | 音频开始播放 | 音量嘴部、柔和光环 | 真实 TTS | 播放结束、被打断或失败 |
| `listening` | 患者开始录音 | 动作减弱、倾听波纹 | 数字人静音 | 录音停止 |
| `thinking` | 上传或分析中 | 慢速状态光 | 默认静音 | 返回结果或错误 |
| `encouraging` | 单项或整组完成 | 一次点头/上浮 | 可选短句 | 动画或播报结束 |
| `error` | TTS、播放或训练动作失败 | 静态人物、错误提示 | 无 | 用户重试或继续训练 |

核心优先级：

```text
患者录音 > 停止命令 > 新任务播报 > 旧任务播报 > 装饰动画
```

任何进入 `listening` 的操作都必须同步执行：

```text
取消未完成的 TTS 请求
-> 停止当前 Audio 元素
-> 断开 AudioContext 分析节点
-> 停止 requestAnimationFrame
-> mouthEnergy 归零
-> 再打开麦克风
```

## 七、真实 TTS 方案

### 7.1 Provider 选择

一期推荐腾讯云基础语音合成：

- 项目已经存在腾讯云 ASR/SOE 的 SecretId、SecretKey 和 SDK 依赖模式。
- 基础接口适合 150 个汉字以内的训练短句。
- 支持语速、音量、采样率、格式和音色配置。
- 可以继续复用后端 Provider 适配层，不让前端接触密钥。
- 新用户可在控制台领取通用语音合成免费资源包，适合答辩和初期试用；免费资源不应被视为正式 SLA。

一期不选择实时 WebSocket TTS。现有训练文案短，先完整生成一段音频再播放，开发和故障处理更简单。后续只有在首包等待明显影响体验时，再升级流式合成。

### 7.2 推荐参数

```text
Provider: tencent
接口: TextToVoice
主语言: 中文
Codec: wav
SampleRate: 24000（所选音色不支持时回退 16000）
Speed: -1 或 -0.5（约 0.8–0.9 倍，最终由试用确定）
Volume: 0
Emotion: neutral / peaceful（仅在音色支持时设置）
文本上限: 150 个中文字符
```

音色选择原则：自然、温和、清晰、不过度幼态，不使用新闻播报或营销腔。答辩前选择 2–3 个候选音色，用同一组康复提示语进行盲听比较，再固定一个默认音色。

建议试听语料：

1. “我们先慢慢来，听完以后再跟着说。”
2. “请跟我说这一句：今天天气很好。”
3. “我在听，你可以按自己的节奏说。”
4. “这一句完成了，我们休息一下，再继续下一句。”
5. “这次没有识别成功，可以重新录一遍。”

### 7.3 TTS Provider 接口

Provider 不应只返回文件路径，而应返回结构化结果：

```python
class TTSResult:
    path: str
    mime_type: str
    provider: str
    voice_id: str
    sample_rate: int
    duration_ms: int | None
```

建议 Provider：

```text
MockTTSProvider       # 测试和无密钥开发
TencentTTSProvider    # 一期真实服务
BrowserTTSFallback    # 前端最终降级，不属于后端 Provider
```

`get_tts_provider()` 必须严格按配置返回 Provider。未知 Provider 应在启动或健康检查时明确报错，不能悄悄返回 mock 并伪装成真实成功。

### 7.4 音频缓存

同一人物音色、语速和文本应复用已生成音频：

```text
cache_key = SHA-256(provider + voice + speed + normalized_text)
```

答辩前预生成固定说明语和常见状态语；动态任务文本按需生成。缓存可降低成本、缩短等待并减少答辩现场网络风险。

## 八、端到端接口设计

保留现有：

```text
POST /api/training/avatar-speech
```

请求体建议扩展为：

```json
{
  "scene": "task_demo",
  "session_id": "uuid",
  "session_task_id": "uuid",
  "text": "请跟我说这一句：今天天气很好。",
  "voice_id": null,
  "speed": -1
}
```

响应体：

```json
{
  "text": "请跟我说这一句：今天天气很好。",
  "audio_file_id": "uuid",
  "audio_url": "/api/files/{file_id}/content",
  "provider": "tencent",
  "voice_id": "default-rehab-voice",
  "fallback": false,
  "cached": false,
  "mime_type": "audio/wav",
  "duration_ms": 3260
}
```

前端不能把 `audio_url` 直接交给 `new Audio(url)`，因为文件接口需要 Bearer Token。正确流程：

```text
Axios GET audio_url, responseType=blob, Authorization=Bearer ...
-> URL.createObjectURL(blob)
-> HTMLAudioElement / AudioContext 播放
-> 播放结束或组件卸载时 revokeObjectURL
```

后端仍返回受保护文件地址，不生成长期公开 URL。

## 九、数据模型

### 9.1 Agent 扩展

建议在 `agents` 表增加：

```text
avatar_runtime_kind        varchar，默认 photo_2_5d
avatar_animation_config    jsonb，可空
tts_voice_id               varchar，可空
tts_speed                  float，默认 -1
```

`avatar_animation_config` 只保存裁剪和动画锚点，不保存完整人脸网格、身份向量或识别结果。

如果一周期限需要严格控制，可先不迁移数据库：答辩版本使用前端自动检测锚点并在当前会话内渲染；试用前再持久化配置。但正式推荐仍是通过迁移保存，以保证不同设备显示一致。

### 9.2 口播事件

答辩版可继续只保存 `generated_audio` 文件资产。投入试用前建议新增 `avatar_speech_events`：

```text
id
patient_profile_id
agent_id
training_session_id
session_task_id
scene
text_hash
audio_file_id
provider
voice_id
fallback
cached
latency_ms
status
error_code
created_at
```

事件表不保存第三方原始异常全文，避免泄露密钥或敏感数据。

## 十、患者端交互设计

### 10.1 创建智能体

把当前一次性表单改为一个短流程：

1. **基本信息**：名称、关系、陪伴风格。
2. **上传正面照**：展示拍摄要求、自动校验、裁剪和动态预览。
3. **选择声音**：试听 2–3 个标准 TTS 音色，默认选中温和平静音色。
4. **授权确认**：形象授权与声音复刻授权分开。使用标准 TTS 时不要求上传声音样本。

上传失败文案应指出可操作原因：

- “没有识别到清晰的正面人脸，请换一张面部更清楚的照片。”
- “照片中检测到多个人，请只保留要创建为陪伴者的人物。”
- “人物面部太小，建议裁剪到胸部以上再上传。”

### 10.2 训练入口

- 默认静音待机，不因页面加载自动播放声音。
- 点击“听数字人说明”后启动 AudioContext，并请求/播放 TTS。
- 加载期间按钮显示“正在准备语音”，但开始训练按钮仍可使用。
- 同一时间只允许一段数字人口播。

### 10.3 训练会话

| 时机 | 状态 | 是否发声 |
| --- | --- | --- |
| 进入任务 | `idle` -> `loading_speech` -> `speaking` | 朗读任务示范 |
| 开始录音 | `listening` | 否，立即停止数字人 |
| 结束录音 | `encouraging` | 默认只显示文字，避免打断试听 |
| 上传分析 | `thinking` | 否 |
| 下一任务 | `speaking` | 简短过渡语 + 新任务 |
| 完成整组 | `encouraging` | 一句短鼓励 |
| 分析失败 | `error` | 默认静音，用户可主动点击重听 |

自动播放必须谨慎：浏览器通常要求音频由用户手势启动。可靠方案是把“开始训练”或“听示范”点击作为首次音频授权动作，之后才能在同一会话中自动播报下一项。

## 十一、异常与降级策略

降级顺序：

```text
缓存的真实 TTS
-> 在线生成真实 TTS
-> 浏览器 speechSynthesis
-> 文字提示 + 状态动画
```

| 异常 | 用户体验 | 系统行为 |
| --- | --- | --- |
| 人脸定位失败 | 要求重新上传；已有头像仍可静态显示 | 禁用局部面部动画 |
| TTS 未配置 | 显示“使用设备语音” | 使用浏览器 TTS |
| TTS 超时 | 训练按钮保持可用 | 取消请求并 fallback |
| 鉴权音频下载失败 | 显示重试按钮 | 不直接访问公开 URL |
| 浏览器禁止自动播放 | 显示“点击播放示范” | 等待用户手势 |
| 播放中开始录音 | 无额外提示 | 强制停止播放后开麦 |
| 任务快速切换 | 只播放最新任务 | runId/AbortController 取消旧任务 |
| AudioContext 不可用 | 语音可播放但无嘴部同步 | 使用 speaking 状态光环 |
| 减少动态效果开启 | 人物保持稳定 | 禁用非必要位移和缩放 |

TTS 失败不得写入空文件资产，也不得把供应商原始异常直接返回前端。

## 十二、隐私、安全与合规

1. 上传前明确确认被拍摄者对形象使用的授权。
2. 标准 TTS 不使用用户声音样本，因此不要求声音授权。
3. 若未来启用声音复刻，单独展示用途、供应商、保存期限和撤回方式。
4. 人脸定位在浏览器本地完成；服务端只保存原图与非身份识别用途的布局锚点。
5. 所有头像和音频继续通过现有文件权限接口访问。
6. 第三方 TTS 密钥只保存在后端环境变量中。
7. 日志不记录原始照片、声音样本、Authorization Header 或供应商密钥。
8. 撤回形象授权后停止新的动画配置生成，并按既有授权策略处理原文件。
9. 页面说明“数字人由系统生成，并非本人实时在线”。

## 十三、性能与可访问性

性能目标：

- 头像动画稳定在 30 FPS 以上，优先目标为 60 FPS。
- 动画只使用 `transform`、`opacity`、Canvas 合成和 `requestAnimationFrame`。
- 同一页面只保留一个活动 AudioContext 和一个动画循环。
- 人脸模型按需懒加载，不阻塞登录和普通训练页面。
- 上传预览使用压缩后的工作图，原始文件仍按现有存储策略保存。
- 常用 TTS 命中缓存时尽量在 500 ms 内进入播放准备状态。
- 在线 TTS 超时建议为 8–10 秒，超时立即降级。

可访问性：

- 动画容器本身 `aria-hidden`，状态文字使用 `aria-live="polite"`。
- 所有动作状态都同时有文字，不能只靠颜色或动画表达。
- 支持 `prefers-reduced-motion`。
- 数字人说话时显示完整字幕。
- 提供停止播报和重复播放按钮。
- 按钮点击区域、字号和对比度沿用患者端低认知负担标准。

## 十六、测试设计

### 16.1 后端

- mock 配置返回 Mock Provider。
- tencent 配置完整时返回 Tencent Provider。
- tencent 配置缺失时健康检查显示 `missing_env`。
- 未知 Provider 不得回退并伪装为 mock 成功。
- 空文本、超过 150 中文字符和越权会话被拒绝。
- TTS 异常不创建空 `FileAsset`。
- 同一缓存键复用同一有效音频。
- 日志和 API 错误不泄露 SecretKey。

### 16.2 前端

- 合格单人正面照通过校验。
- 无人脸、多人、侧脸和面部过小得到明确错误。
- 锚点识别失败后能够降级静态动画。
- 真实音频通过 Authorization Blob 播放。
- 音量增加时 `mouthEnergy` 平滑增加。
- 播放结束、停止、路由离开后资源全部清理。
- 快速点击不同示范只保留最后一次。
- 录音开始前没有任何数字人口播残留。
- TTS 失败后浏览器 TTS 或文字模式仍可训练。
- `prefers-reduced-motion` 下无明显平移和缩放。

### 16.3 试用前人工观察

- 患者是否能理解当前轮到谁说。
- 数字人动作是否造成分心或不适。
- 语速是否足够清楚但不过慢。
- 字幕和声音是否一致。
- 患者是否会误以为嘴型是标准构音示范。
- 陪伴形象是否提高了继续训练的意愿。

## 十七、验收标准

答辩版本必须同时满足：

1. 上传合规正面照后可看到自动居中和动态预览。
2. 待机、说话、倾听、思考、鼓励和错误状态可辨认。
3. 至少一个训练入口和一个训练任务使用真实中文 TTS。
4. 嘴部/下半脸运动来自实际音频能量，而非随机定时器。
5. 数字人播报和患者录音不会重叠。
6. TTS 或网络失败不阻塞训练。
7. 受保护音频不通过公开裸链接播放。
8. 页面持续显示文字字幕并支持停止、重播。
9. Chrome 与 Edge 答辩设备实测通过。
10. 后端测试、患者闭环烟测和前端生产构建通过。

## 十八、风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 局部嘴部变形显得不自然 | 降低可信度 | 控制幅度；低质量锚点只显示音量光环 |
| 正面照仍难以定位 | 无法启用增强动画 | 上传前校验；允许换图；保留基础动画 |
| TTS 首次生成慢 | 患者等待 | 缓存固定语句；显示准备状态；允许跳过 |
| 浏览器阻止自动播放 | 无声音 | 首次播放绑定用户点击 |
| 答辩网络故障 | 真实 TTS 不可用 | 提前生成缓存；浏览器 TTS；本地录屏备份 |
| 动画被理解为精确示范 | 康复信息误导 | 明确陪练定位；不用“看嘴型学习”文案 |
| 上传照片涉及隐私 | 合规风险 | 授权确认、本地定位、鉴权访问、撤回机制 |
| 动作影响注意力 | 患者负担 | 小幅低频；减少动态效果；试用观察 |

## 十九、后续升级路线

### Phase 1：答辩版

正面照校验、基础 2.5D、音量嘴部、真实非流式 TTS、缓存与降级。

### Phase 2：小规模试用版

手动锚点校准、口播事件表、音色设置、延迟和失败率监控、跨设备一致性。

### Phase 3：个性化声音

在单独授权、撤回和供应商数据治理完成后接声音复刻；标准 TTS 始终保留为 fallback。

### Phase 4：精确口型或高级数字人

若临床需求明确要求构音可视化，再评估中文 viseme 时间戳、专门录制的构音教学视频或经过验证的 3D 口腔模型。高级视觉能力继续作为可替换 Provider，不进入训练评分核心链路。

## 二十、答辩表达建议

推荐将成果描述为：

> 我们没有采购高成本云端视频数字人，而是针对康复场景实现了轻量、隐私友好的照片数字人运行时。系统对取得授权的正面人物照片进行本地人脸定位，通过分层 2.5D 动画表达陪伴状态；后端真实 TTS 负责自然中文口播，前端实时分析音频能量驱动说话动作。它能在录音、分析和任务切换中被可靠打断，并在网络失败时自动降级，因此既适合答辩展示，也具备进入小规模试用的工程基础。
