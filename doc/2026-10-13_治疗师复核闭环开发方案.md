# 治疗师复核闭环开发方案

> 版本：v1.0  
> 日期：2026-10-13  
> 目标分支：`new-UI`  
> 状态：待确认后实施  
> 适用范围：Product V2 治疗师端、Evaluation Run V3、训练方案版本系统

## 1. 方案摘要

本方案把目前分散在工作台、训练详情、旧评估页、Stage Review 和训练方案页中的能力，串成一条治疗师可以从头走到尾的工作流：

```text
发现待办
→ 接手并锁定负责人
→ 查看患者身份、原音、转写、自动证据和质量状态
→ 确认 / 修正 / 标记无法判断
→ 形成阶段复核快照
→ 作出专业决定
→ 必要时生成并编辑新方案版本
→ 发布新方案或记录无需调整
→ 写入处理结果并关闭待办
```

本轮不新建一套平行的“复核业务系统”。实现应优先复用：

- `AttentionItem`：复核入口、负责人、工作状态；
- `EvaluationRun`：不可变的自动评估结果；
- `EvaluationReviewRevision`：人工确认、修正、无法判断及审计；
- `StageReview`：阶段事实快照；
- `TherapistDecision`：最终专业决定；
- `TrainingPlanVersion`：由决定产生的新方案草稿；
- `EvidenceRecord` / `MetricRecord`：来源证据、质量和指标。

核心产品原则：

1. 原始录音、原始转写和自动结果不可被覆盖；人工修订以新记录追加。
2. 系统建议不能直接修改正式训练方案。
3. 创建方案草稿不等于处理完成；涉及方案调整的待办必须等新方案发布或明确放弃后才能关闭。
4. 技术失败、低质量音频和证据不足不能被人工“确认”为有效能力下降。
5. 治疗师在做决定时始终能看到患者身份、证据时间范围和当前方案版本。

## 2. 当前实现盘点

### 2.1 已有能力

#### 待办

`AttentionItem` 已包含：

- `patient_profile_id`
- `item_type` / `trigger_code`
- `trigger_facts`
- `source_refs` / `evidence_ids`
- `priority` / `summary`
- `status`
- `assigned_to_user_id`
- `acknowledged_at`
- `resolved_at` / `resolution_note`

后端已经支持：

- 查询治疗师工作台；
- 接手待办；
- 解决或忽略待办；
- 按患者分配关系做权限限制。

#### 原始证据与自动评估

- 跟读训练：`Attempt`、音频文件、ASR/声学/发音分析、`EvaluationRun(domain=repeat)`；
- 场景表达：`ScenarioDialogueSession`、逐轮音频和转写、语义证据、`EvaluationRun(domain=functional_communication)`；
- `EvaluationDimensionResult` 保存维度结果和证据快照；
- `EvaluationReviewRevision` 保存自动值快照、修订值、证据覆盖、理由和复核人；
- 评估运行采用 candidate/adopted/superseded，适合保留完整修订历史。

#### 阶段复核和方案调整

- `StageReview` 能冻结事实、观察、建议、待办、正式评估和 Clinical Stage 引用；
- `TherapistDecision` 保存决定类型、理由、输入和结果；
- `create_new_training_plan_version` 能复制当前方案及练习规则，形成新草稿；
- `TrainingPlanVersion.source_decision_id` 可以追溯方案来源；
- 发布新方案时会原子替换当前 active 版本。

### 2.2 当前断点

1. 工作台卡片不能直接进入统一复核页面，只能跳患者页或创建 Stage Review。
2. V2 练习详情缺少原音回听、完整转写、人工确认和修正表单。
3. `EvaluationReviewRevision` 的接口目前偏向场景表达，没有按 EvaluationRun domain 做统一分发。
4. `attention_dict()` 没有返回负责人、接手时间和处理备注，前端无法展示协作状态。
5. 创建 Stage Review 时默认把患者所有开放待办放入快照，无法清楚区分“本次复核的来源待办”。
6. 创建新方案草稿后，当前逻辑立即解决来源待办，但草稿尚未发布。
7. 训练方案草稿不能编辑、排序、预览或比较版本。
8. Stage Review 页面缺少患者身份、触发原因、复核窗口和最终决定回显。

## 3. 目标与非目标

### 3.1 本期目标

完成以下闭环：

- 治疗师可以按负责人、优先级、类型和状态处理待办；
- 每条待办都能定位到具体训练、练习、Attempt/Dialogue 和 EvaluationRun；
- 治疗师可以在一个页面内回听原音、核对转写、查看证据与质量门控；
- 对每个 EvaluationRun 执行确认、修正或无法判断；
- 修正不覆盖原始数据，并生成新的 adopted EvaluationRun 或追加确认记录；
- 从待办直接创建一次聚焦的 Stage Review；
- 最终决定可以保持方案、请求正式评估、记录观察或生成新方案草稿；
- 新方案经过编辑和发布后，再关闭需要调整方案的待办；
- 所有关键动作可以追溯到操作者、时间、理由和前后状态。

### 3.2 非目标

本期明确不做：

- 自动批准系统建议；
- 自动发布训练方案；
- 让大模型直接生成临床结论；
- 把治疗师人工修订回写覆盖原始 ASR 或原始自动指标；
- 新建在线聊天或远程诊疗系统；
- 在同一期完成全部 WAB/CADL 模板化录入；
- 重构患者训练页面。

---

## 4. 用户角色和权限

### 4.1 治疗师

只能查看和处理自己处于 active assignment 的患者：

- 查看待办和证据；
- 接手待办；
- 追加评估复核修订；
- 创建和完成 Stage Review；
- 创建方案草稿；
- 编辑并发布由本人或同一患者复核产生的草稿；
- 关闭本人接手的待办。

### 4.2 管理员

拥有治疗师能力，并可处理所有患者；可重新分配待办负责人，但不能静默覆盖已有专业决定。

### 4.3 患者与家属

本期不开放专业复核页面、自动证据内部字段、复核理由和版本 diff。

患者端只接收最终安全结果，例如“治疗师已调整后续训练安排”，不得显示内部 reason code。

## 5. 核心工作流

### 5.1 步骤一：待办分诊

### 页面

路由：`/therapist/reviews`

工作台保留摘要，但“需要处理的事项”进入独立复核队列页面。

### 队列默认排序

```text
高优先级未接手
→ 患者主动求助
→ 技术/数据冲突
→ 已接手且等待处理
→ 普通趋势异常
→ 评估到期
```

同一优先级按触发时间从早到晚排序。

### 筛选

- 状态：待处理、我已接手、等待补充、等待方案发布；
- 类型：患者求助、持续困难、无法评分、坚持度下降、评估到期、数据异常；
- 优先级：高、普通、低；
- 患者姓名；
- 时间范围。

### 卡片必须显示

- 患者姓名；
- 触发原因的中文标签；
- 一句话摘要；
- 优先级；
- 触发时间；
- 负责人和接手时间；
- 关联证据数量；
- 当前下一步，例如“需要复核 1 次跟读结果”。

### 操作

- `接手并开始复核`
- `继续复核`
- `查看患者`
- 管理员可 `转交`

接手接口必须幂等：同一操作者重复调用返回当前记录；若已被其他治疗师接手，返回 409 和接手人信息，不允许静默抢占。

---

### 5.2 步骤二：原音、转写和证据核对

### 页面

路由：`/therapist/reviews/:attentionItemId`

页面采用单一任务布局，不做多模块仪表盘。

### 固定上下文栏

始终显示：

- 患者姓名；
- 当前康复目标；
- 当前方案版本与阶段重点；
- 待办类型、优先级、触发时间；
- 当前负责人；
- 数据时间范围；
- 返回队列入口。

### 主体顺序

1. 为什么需要复核；
2. 原始材料；
3. 系统如何判断；
4. 人工复核操作；
5. 下一步。

### 原始材料区域

#### 跟读

- 目标句；
- 原始录音播放器；
- ASR 原始转写；
- 录音时长、提示等级、开始等待时间；
- 录音质量：过短、安静、噪声、削波；
- provider、模型/算法版本；
- 是否发生 fallback；
- 原始 Attempt 时间。

#### 场景表达

- 场景目标与角色；
- 任务契约版本；
- 完整多轮对话；
- 每个患者回合的原音播放器；
- 每个回合的 ASR 转写；
- 系统识别的信息单元、原话引用和置信度；
- 提示、修复和追问过程；
- 最终目标达成状态。

### 系统证据区域

按“测量事实”展示，不直接用 JSON：

- 维度名称；
- 自动值/等级；
- 状态：已测得、未观察、不可用、需要复核；
- 单位；
- 证据引用；
- 质量门控；
- 是否允许进入画像；
- 局限说明。

内部 JSON 仅放在折叠的“技术详情”中，默认关闭。

### 音频不可用状态

若文件丢失或无权限：

- 页面不能假装可复核；
- 对依赖原音的维度只允许选择“无法判断”；
- 显示恢复建议；
- 记录 `audio_unavailable` 原因；
- 允许保留待办为“等待补充”，不得强制关闭。

---

### 5.3 步骤三：人工确认、修正或无法判断

### 复核动作

每个 EvaluationRun 提供三种动作：

#### 确认 `confirmed`

含义：治疗师核对原始证据后，同意当前自动结果。

要求：

- 至少播放过原音不是强制后端条件，但前端记录 `audio_opened_at` 供审计；
- 可填写补充说明；
- 不创建新的 EvaluationRun，只追加 `EvaluationReviewRevision`。

#### 修正 `corrected`

含义：自动结果与原始证据不一致。

要求：

- 必须选择被修正的维度；
- 必须填写修正后的状态和值/等级；
- 必须填写理由；
- 场景信息单元修正必须引用患者原话或标记“原音可判断但转写错误”；
- 系统根据原运行和人工 override 生成新的 candidate run；
- 原子地将新 run 设为 adopted，并把旧 run 设为 superseded；
- 修订记录关联旧 run 和新 run。

#### 无法判断 `unjudgeable`

适用于：

- 原音不可用；
- 噪声严重；
- 转写与原音均不足以判断；
- 任务契约不适用；
- 患者实际未完成该维度。

要求：

- 必须选择原因码；
- 对应维度变为 `unavailable` 或 `not_observed`；
- 不能进入正式画像或趋势；
- 可选择“建议患者重录”或“转为正式评估”。

### 复核提交确认

提交前显示摘要：

```text
患者：张某
练习：医院就诊场景
动作：修正
维度：信息完整度
自动结果：部分达成
人工结果：已达成
依据：患者第 2 回合原音与转写
```

确认按钮文案使用具体动作，例如“确认并保存修正”，不用泛化的“提交”。

### 防重复

前端生成 `review_request_key`；后端对同一 run、reviewer 和 key 幂等。网络超时后重新提交不得产生第二条修订。

---

### 5.4 步骤四：形成阶段复核

单次证据复核完成后，治疗师有两个出口：

1. `保存复核并返回队列`：适合技术误差或无需改方案的事项；
2. `进入阶段决策`：适合持续困难、趋势变化、患者求助或需要调整计划的事项。

### 创建规则

- 从待办进入时，只把当前待办作为 primary source；
- 可勾选同一患者其他开放待办一并处理；
- Stage Review 固化创建时的事实，后续新训练不反向改变该复核；
- 记录患者、当前目标、当前方案版本、复核时间窗和来源待办；
- 已存在同一 primary attention 的 draft Stage Review 时直接复用，不重复创建。

### Stage Review 页面结构

#### 顶部身份区

- 患者姓名；
- 复核编号；
- 当前计划 vN；
- 观察时间范围；
- 触发原因；
- 创建人和创建时间。

#### 四层语义

1. 事实：原始训练、人工复核后的 adopted 结果、正式评估；
2. 观察：系统生成的保守观察与治疗师补充观察；
3. 候选建议：仅供参考；
4. 治疗师决定。

页面不得只显示内部 ID、reason code 或原始 JSON。

---

### 5.5 步骤五：专业决定

支持以下决定：

| 决定 | 后续动作 | 待办状态 |
|---|---|---|
| 继续当前方案 | 记录决定 | 可关闭 |
| 暂不调整、继续观察 | 记录观察截止日期 | 等待随访或关闭 |
| 请求正式评估 | 创建评估待办 | 当前待办可关闭，新待办打开 |
| 添加专业记录 | 保存记录 | 可关闭 |
| 调整阶段重点 | 生成新方案草稿 | 等待方案发布 |
| 调整策略/练习 | 生成新方案草稿 | 等待方案发布 |
| 无需处理/误报 | 记录理由 | dismissed |

### 决定前确认

必须展示：

- 患者身份；
- 决定类型；
- 决定理由；
- 是否生成方案草稿；
- 将影响哪些待办；
- 待办是立即关闭还是等待方案发布。

### 重要状态修正

当前 `create_decision()` 在生成新方案草稿后会立即解决来源待办，应调整为：

```text
决定无需改方案
→ 可立即 resolved/dismissed

决定需要新方案
→ attention.status = waiting_plan_publish
→ 创建 draft plan
→ 治疗师编辑并发布
→ 发布成功后 resolved
```

如果治疗师放弃草稿：

- 必须填写原因；
- 可回到 Stage Review 选择其他决定；
- 待办不能静默消失。

---

### 5.6 步骤六：调整并发布方案

### 从决定进入方案编辑器

路由：`/therapist/plans/:planId/edit?sourceReview=:reviewId`

新草稿默认复制：

- 当前康复目标；
- 阶段重点；
- 训练频率和时长；
- 练习顺序；
- 难度；
- 提示策略；
- 场景范围。

### 编辑能力

- 修改阶段重点；
- 添加/删除练习；
- 上移、下移或拖拽排序；
- 设置 warmup/main/consolidation/challenge；
- 设置单题难度、重复次数、最大信息单元和提示策略；
- 显示总预计时长；
- 查看与 active 版本的 diff；
- 患者视角预览；
- 保存草稿；
- 废弃草稿；
- 正式发布。

### 发布前检查

- 至少一个练习；
- order_index 唯一且连续；
- 总时长不超过产品设定上限；
- 任务模板仍处于 active；
- 方案关联当前有效康复目标；
- active 方案未在编辑期间被其他人替换。

最后一项使用 `base_plan_version_id` 或 `expected_active_plan_id` 做并发检查；冲突时返回 409，并展示版本差异，不覆盖他人方案。

### 发布后的联动

发布事务完成后：

1. 新方案变为 active；
2. 旧方案变为 superseded；
3. `TherapistDecision.result_snapshot` 补充 published plan 信息；
4. 来源待办变为 resolved；
5. 写入关闭说明：“阶段复核决定生成并发布训练方案 vN”；
6. 患者首页出现安全通知：“治疗师已更新后续训练安排”。

---

### 5.7 步骤七：关闭与留痕

关闭待办必须记录：

- 处理结果码；
- 人类可读处理说明；
- 处理人；
- 处理时间；
- 关联 EvaluationReviewRevision；
- 关联 Stage Review；
- 关联 TherapistDecision；
- 关联新方案版本（如有）。

推荐处理结果码：

```text
confirmed_no_change
corrected_no_plan_change
plan_updated
formal_assessment_requested
waiting_for_more_evidence
technical_issue_only
duplicate
false_positive
patient_contact_required
```

关闭后记录只读；若后续需要重新处理，应创建新待办并引用旧待办，而不是重新打开并覆盖历史。

## 6. 状态机设计

### 6.1 AttentionItem 状态

```text
open
  ├─ acknowledge → acknowledged
  ├─ dismiss → dismissed
  └─ merge → resolved

acknowledged
  ├─ begin review → in_review
  ├─ wait for evidence → waiting_information
  ├─ release → open
  └─ dismiss → dismissed

in_review
  ├─ decision needs no plan → resolved
  ├─ decision creates draft → waiting_plan_publish
  ├─ insufficient evidence → waiting_information
  └─ cancel draft review → acknowledged

waiting_information
  ├─ evidence available → in_review
  └─ close without conclusion → resolved

waiting_plan_publish
  ├─ plan published → resolved
  ├─ draft abandoned → in_review
  └─ conflict → waiting_plan_publish
```

终态：`resolved`、`dismissed`。

开放待办去重索引必须覆盖：

```text
open, acknowledged, in_review, waiting_information, waiting_plan_publish
```

### 6.2 StageReview 状态

```text
draft → ready_for_decision → finalized
```

- `draft`：允许补充治疗师备注、关联复核结果；
- `ready_for_decision`：事实快照完整，可以提交决定；
- `finalized`：不可原地修改，纠错需创建 successor review。

### 6.3 TrainingPlanVersion 状态

沿用：

```text
draft → active → superseded
```

增加 `abandoned`，用于明确记录由阶段决定创建但最终未采用的草稿。

## 7. 数据模型改造

```text
type=
priority=
```

保持现有路径，补充并发和幂等语义。

### `POST /api/v2/therapist/attention-items/{id}/release`

释放本人接手、尚未开始正式复核的待办。

### `POST /api/v2/therapist/attention-items/{id}/reassign`

仅管理员；记录事件，不覆盖历史。

### 8.2 统一复核证据包

```json

  "goal": {},
  "active_plan": {},
```

服务端负责解析 `source_refs`；前端不得根据 JSON 猜测实体类型。

### 8.3 EvaluationRun 复核

### 8.4 Stage Review

替代前端先跳患者页再创建复核的绕行。

```json
  "review_to": null,
```

返回完整草稿、规则、来源决定和 active 版本摘要。

### `PATCH /api/v2/therapist/training-plans/{id}`

仅 draft 可编辑；支持完整替换 exercise rules。

### `POST /api/v2/therapist/training-plans/{id}/abandon`

必须提供原因；若来源待办正在等待发布，则返回 Stage Review 继续决策。

## 10. 页面状态与异常处理

每个主页面必须覆盖：

### 加载

- 队列骨架；
- 证据包分区加载；
- 音频独立加载失败不阻断文字证据。

### 空状态

- 无待办：说明正常训练仍可在患者工作区查看；
- 无原音：解释无法判断的处理方式；
- 无 EvaluationRun：允许标记技术问题并转排障；
- 无正式评估：不能暗示为 0 分。

### 权限变化

若治疗师打开页面后 assignment 被撤销：

- 后端返回 403；
- 前端停止展示缓存证据；
- 返回队列并提示权限已变化。

### 并发冲突

- 待办被他人接手：显示负责人和时间；
- Stage Review 已 finalized：切换为只读；
- active plan 已变化：阻止发布并显示 diff；
- 同一修订重复提交：返回原结果。

### 网络超时

- 不显示“保存失败”后允许盲目重复创建；
- 使用 request key 查询提交结果；
- 对复核和决定提供“检查保存状态”。

### 未保存离开

以下页面使用 route leave guard：

- 人工修正表单；
- Stage Review 决定表单；
- 方案草稿编辑器。

提示选项：继续编辑、保存草稿、放弃修改。

- 音频播放器必须支持键盘播放、暂停、前进/后退 5 秒和倍速；

## 12. 后端服务分层

建议新增模块：

```text
backend/app/modules/review_workflow/
  __init__.py
  router.py
  schema.py
  service.py
  model.py          # AttentionItemEvent
  bundle.py         # source_refs → 统一证据包
  transitions.py    # 状态机和权限
```

职责边界：

- `bundle.py` 只组装只读证据，不产生临床决定；
- `transitions.py` 只处理合法状态变化；
- EvaluationRun 修订仍放在 `evaluation_runs` domain handler；
- Stage Review 和 Plan 的核心写操作继续由 `product_v2` 服务提供；
- `review_workflow.service` 只负责编排事务，不复制评分逻辑。

禁止：

- 在前端重新计算指标；
- 在 review workflow 里复制跟读/场景评分规则；
- 直接 update 原始 EvaluationDimensionResult；
- 通过修改 JSON 快照伪装完成复核。

## 16. 验收标准

### 场景 A：确认自动结果，无需改方案

1. 治疗师在队列看到患者求助待办；
2. 接手后显示本人和时间；
3. 能回听原音并查看转写；
4. 确认自动维度；
5. 复核记录包含自动值、复核人和时间；
6. 决定继续当前方案；
7. 待办以 `confirmed_no_change` 关闭；
8. 患者训练计划不发生变化。

### 场景 B：修正场景证据并调整方案

1. 治疗师发现 ASR 漏识别信息单元；
2. 使用患者原话修正；
3. 原 EvaluationRun 保留，新 run adopted；
4. 创建 Stage Review；
5. 决定调整训练方案；
6. 待办进入 `waiting_plan_publish`，不能提前关闭；
7. 新草稿复制旧方案并可编辑排序；
8. 发布成功后待办关闭；
9. 新方案可追溯到 decision 和 stage review；
10. 患者首页看到计划更新通知。

### 场景 C：证据不可判断

1. 原音文件不可用或质量不合格；
2. 页面明确禁止确认依赖原音的维度；
3. 治疗师标记无法判断并选择原因；
4. 结果不进入画像与趋势；
5. 可创建重录/正式评估待办；
6. 原待办进入等待补充或以 technical_issue_only 关闭。

### 场景 D：多人并发

1. 治疗师 A 接手待办；
2. 治疗师 B 再接手收到 409 和负责人信息；
3. A 编辑方案期间 active plan 被更新；
4. A 发布收到冲突和版本 diff；
5. 系统不覆盖新 active plan，也不提前关闭待办。

### 通用验收

- 所有写操作有明确成功状态；
- 所有关键写操作幂等；
- 页面不直接显示内部枚举；
- 原始录音、原始转写、自动结果不可被覆盖；
- 未分配治疗师不能读取证据包；
- 患者/家属无法访问专业复核接口；
- 技术失败不进入能力下降结论；
- 任何关闭待办都可追溯到处理人和依据。

## 17. 可观测性

新增结构化事件：

```text
review_queue_loaded
attention_acknowledged
attention_conflict
review_bundle_loaded
review_audio_opened
evaluation_review_confirmed
evaluation_review_corrected
evaluation_review_unjudgeable
stage_review_created
stage_review_reused
therapist_decision_recorded
plan_draft_created_from_decision
plan_publish_conflict
plan_published_from_review
attention_resolved_from_review
```

日志不得包含：

- 原始音频内容；
- 完整患者转写；
- 治疗师自由文本全文；
- API key 或第三方原始异常。

建议运营指标：

- 待办首次接手时长；
- 从接手到关闭时长；
- 确认/修正/无法判断比例；
- 因音频不可用无法判断的比例；
- 产生方案草稿后最终发布率；
- 待办被重新分配比例；
- 发布冲突次数。

这些指标只用于流程质量，不用于评价治疗师绩效。

## 18. 风险与控制

| 风险 | 控制 |
|---|---|
| 人工修正被误当成原始事实 | append-only revision，保留 automatic snapshot |
| 一个待办关联多个来源导致页面混乱 | review bundle 服务端标准化、primary source 明确 |
| 草稿未发布却提前关闭待办 | `waiting_plan_publish` 中间状态 |
| 治疗师处理错患者 | 固定患者身份栏、提交摘要二次确认 |
| 两人同时处理同一待办 | 接手冲突 409、负责人可见、管理员转交 |
| 多人同时发布方案 | expected active plan 乐观锁 |
| 网络超时产生重复决定 | request key 幂等 |
| 旧数据无法解析 | 回退旧页面、逐步补 source_refs，不伪造证据 |
| 页面泄漏敏感技术数据 | 专业权限检查、技术详情折叠、日志脱敏 |

## 19. 中期答辩最小可演示版本

如果时间有限，最小演示闭环只做以下内容：

1. 工作台增加“待复核”入口；
2. 待办卡显示患者、原因、原始练习和接手人；
3. 统一复核页展示一条跟读或场景训练的原音、转写、证据和质量；
4. 支持确认或修正一个维度；
5. 创建 Stage Review 并显示患者上下文；
6. 选择“生成新方案草稿”；
7. 跳转到现有训练方案页查看草稿；
8. 发布后自动关闭待办并显示完整处理结果。

答辩演示推荐使用“场景表达 ASR 漏识别关键词”的案例，因为它能直观体现：

```text
AI 提取证据
≠ 自动临床决定

治疗师回听原音
→ 修正证据
→ 形成阶段决定
→ 调整训练方案
→ 全流程可追溯
```

## 20. 实施决策

本方案默认采用以下决定，开发时不再临时发明：

1. `AttentionItem` 是工作入口，不新增平行 ReviewTask 主表；
2. `EvaluationReviewRevision` 是人工修订唯一事实源；
3. `StageReview` 是阶段决策快照，不承担逐条音频修订；
4. `TherapistDecision` 是最终专业决定；
5. `TrainingPlanVersion` 只有发布后才改变患者后续正式训练；
6. 需要新方案的待办在发布前保持 `waiting_plan_publish`；
7. 所有修订、决定和发布均采用幂等 key；
8. 新页面只展示结构化专业信息，原始 JSON 降级到技术详情；
9. 旧复核页面在迁移完成前保留；
10. R1～R3 作为第一交付里程碑，R4 完成真正业务闭环。
