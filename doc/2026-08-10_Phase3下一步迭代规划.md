# 2026-08-10 Phase 3 下一步迭代规划

## 1. 背景

Phase 2 的五个阶段已经完成并测试通过：

- Phase 2.1：建立康复评价指标字典和单次作答评价数据模型。
- Phase 2.2：在作答分析后自动写入过程性监控指标。
- Phase 2.3：将训练反馈从旧的综合分结构切换为 `process_metrics + feedback[]`。
- Phase 2.4：新增阶段性评估系统，支持 WAB、CADL、接受度等训练前后对比数据。
- Phase 2.5：新增患者端 `/evaluation` 页面，展示当前指标、趋势图、阶段评估对比和雷达图。

当前系统已经具备“训练 -> 分析 -> 过程性监控 -> 阶段评估 -> 患者端展示”的评价闭环。下一轮迭代不建议继续优先扩展展示型页面，而应把 Phase 2 产生的数据进一步用于报告、能力画像和训练策略调整。

## 3. 当前阶段判断

### 已完成能力

- 患者端基础闭环已经成立：注册登录、智能体创建、训练、录音、分析、反馈、记录。
- 评价模型已从旧的“综合分 + 五维分”转向“过程性监控 + 阶段性效果对比”。
- 数据库已经有 `evaluation_metrics`、`attempt_evaluations`、`assessment_sessions`。
- `/evaluation` 已经可以展示过程性趋势和阶段性对比。
- AI 相关能力仍处于 Mock Provider 阶段，但接口边界已经为真实 ASR、声学分析和 LLM 反馈预留。

### 主要短板

- `/api/reports/latest` 和患者端 `/report` 仍偏旧逻辑，核心仍是 `average_score`，与 Phase 2 的新评价体系不一致。
- 阶段性评估目前主要依赖接口录入，缺少患者端或辅助录入入口。
- 系统尚未形成 `ability_profiles` 能力画像，Phase 2 指标还没有反向驱动训练难度和提示策略。
- 训练题目和训练计划仍偏静态，尚未真正使用“内容难度 L1-L5 × 自主程度 S1-S4”。
- Mock ASR、Mock 声学分析和旧 LLM 评分残留仍存在，需要逐步收口到可替换的真实分析链路。

## 4. Phase 3 推荐主题

Phase 3 推荐主题：

```text
从“能展示评估结果”升级为“能基于评估结果生成报告和调整训练”。
```

核心目标：

1. 把报告系统迁移到 Phase 2 的过程性监控和阶段性评估数据。
2. 建立患者能力画像，让系统知道患者当前处于什么训练水平。
3. 用能力画像驱动下一次训练推荐，形成初步自适应训练闭环。
4. 保持 Mock AI 可运行，同时为真实 ASR 和声学分析替换打好接口与数据基础。

## 5. 建议拆分

### Phase 3.1 报告系统重构

目标：

- 将 `/api/reports/latest` 从旧 `AttemptScore.overall_score` 聚合，迁移到 `attempt_evaluations` 和 `assessment_sessions`。
- 患者端 `/report` 不再显示“平均分”，改为显示过程性监控汇总、阶段性变化和下一步建议。

后端建议：

- 更新 `backend/app/modules/reports/schema.py`。
- 更新 `backend/app/modules/reports/service.py`。
- 保留 `GET /api/reports/latest`，但返回结构调整为 API V2 文档中的方向：

```json
{
  "training_count": 10,
  "process_monitoring_summary": {
    "avg_script_accuracy": 96.5,
    "avg_error_count": 1.2,
    "avg_speech_rate": 175,
    "avg_loudness": 64
  },
  "effect_comparison": {
    "wab": {},
    "cadl": {},
    "acceptance": {}
  },
  "suggestion": "继续加强脚本输出稳定性，并观察阶段性WAB/CADL变化。"
}
```

前端建议：

- 更新 `frontend/src/types/api.ts`。
- 更新 `frontend/src/api/reports.ts`。
- 重构 `frontend/src/views/patient/ReportView.vue`。

验收标准：

- `/report` 页面不再出现“平均分”。
- 没有训练数据时显示清晰空态。
- 有训练数据时展示最近训练次数、四个过程性指标均值和建议。
- 有 baseline/current assessment 时展示训练前后变化摘要。
- 后端不再依赖 `overall_score` 生成报告建议。

### Phase 3.2 患者端康复记录纠偏

目标：

- 移除患者端专业量表录入和专业术语。
- 将患者端 `/evaluation` 和 `/report` 改为低认知负担的康复记录。
- 将过程性指标转译为患者能理解的表达。

患者端展示原则：

- `script_accuracy` 展示为“表达完整度”。
- `error_count` 展示为“需要留意的地方”。
- `speech_rate` 展示为“说话节奏：偏慢 / 合适 / 偏快”。
- `loudness` 展示为“声音状态：偏轻 / 稳定 / 偏响”。

患者端不展示：

- WAB。
- CADL。
- baseline。
- after_30_days。
- dBA。
- 字/min。
- 阶段性量表录入表单。
- 专业雷达图。

验收标准：

- 患者端 `/evaluation` 和 `/report` 不再出现专业术语。
- 患者端能看到最近训练次数、表达完整度、需要留意的地方、说话节奏、声音状态。
- 患者端只显示简化建议，不显示专业量表明细。
- 后端仍保留专业数据结构，后续供治疗师端使用。

### Phase 3.3 角色边界与路由骨架

目标：

- 明确患者端、家属端、治疗师端的信息架构。
- 为家属端和治疗师端预留前端路由、布局和后端权限边界。
- 暂不把专业量表放回患者端。

### Phase 3.4 治疗师端阶段性评估录入

目标：

- 将 `POST /api/assessment` 的 WAB、CADL、接受度录入入口放到治疗师端。
- 支持查看阶段评估历史和训练前后对比。
- 患者端只消费治疗师录入后的简化结论。

### Phase 3.5 能力画像 MVP

目标：

- 新增 `ability_profiles`，把患者近期过程性监控和阶段性评估沉淀为当前能力状态。
- 为后续训练推荐提供统一输入。

数据建议：

新增表：

```text
ability_profiles
```

核心字段：

- `patient_profile_id`
- `current_content_level`：L1-L5
- `current_autonomy_level`：S1-S4
- `avg_script_accuracy_recent`
- `avg_error_count_recent`
- `avg_speech_rate_recent`
- `avg_loudness_recent`
- `assessment_summary`
- `confidence`
- `updated_at`

可选新增：

```text
ability_profile_snapshots
```

如果想控制 Phase 3.3 规模，可以先不做 snapshots，只在 Phase 3.4 或 Phase 4 增加。

后端建议：

- 新增 `backend/app/modules/profiles/`。
- 新增 `GET /api/profile/ability`。
- 新增内部服务 `refresh_ability_profile(patient_profile_id)`。
- 在训练分析完成后，基于最近 N 次有效 `attempt_evaluations` 更新能力画像。
- 在阶段性评估创建后，也触发能力画像刷新。

初版规则建议：

- `script_accuracy >= 90` 且 `error_count <= 1`，可考虑提高内容难度。
- `script_accuracy < 70` 或 `error_count >= 4`，应降低难度或增加提示。
- `speech_rate < 180`，建议增加连续表达训练。
- `loudness < 60`，建议增加响度稳定练习。
- 规则必须写在后端，前端只展示结果。

验收标准：

- 完成一次训练分析后，能力画像可刷新。
- 完成一次阶段评估后，能力画像可刷新。
- `GET /api/profile/ability` 返回当前 L/S 等级、近期指标和建议。
- 没有足够数据时返回低置信度状态，而不是伪造结论。

### Phase 3.6 初步自适应训练推荐

目标：

- 让训练入口不只是固定任务，而是能根据能力画像推荐下一次训练类型、内容难度和提示等级。

后端建议：

- 更新 `GET /api/training/today`。
- 更新 `POST /api/training/session`。
- 为训练任务补充或规范化：
  - `content_level`：L1-L5
  - `autonomy_level`：S1-S4
  - `prompt_level`
  - `target_metric`

推荐规则初版：

- 若脚本正确率稳定且错误少，下一次提高 L 或 S。
- 若错误多，优先降低 S 或提高提示等级。
- 若语速偏慢，推荐短句连续表达。
- 若响度偏低，推荐带响度目标的跟读训练。
- 若阶段性评估缺失，优先在治疗师端提醒补充训练前评估。

前端建议：

- 首页显示“今日建议训练”。
- 训练开始页展示推荐原因，例如“最近语速偏慢，今天先练连续短句表达”。
- 不让患者面对复杂参数，只保留“开始训练”和“换一个任务”。

验收标准：

- 不同能力画像能得到不同推荐。
- 推荐结果可追溯到最近过程性指标。
- 患者仍可顺畅完成训练流程。
- 推荐失败时回退到默认训练任务。

### Phase 3.7 真实分析链路预备

目标：

- 将 Mock 分析链路收口为可替换的真实 ASR、声学分析、规则评价和 LLM 反馈结构。
- 不要求一次性接入真实供应商，但要把接口边界、配置和错误状态整理清楚。

建议工作：

- 梳理 `backend/app/integrations/asr/`、`acoustic_analysis/`、`llm/` 的统一 Provider 协议。
- 将旧 LLM `overall_score` 输出降级为兼容字段或内部历史残留，不再作为主业务依据。
- 在 `attempt_analysis_results` 中保存更完整的原始分析结构：
  - transcript
  - speaking_duration_seconds
  - loudness_dba
  - long_pause_over_3s_count
  - error_events
  - provider_name
  - provider_version
- 明确分析失败时不更新 `attempt_evaluations` 和能力画像。

验收标准：

- Mock Provider 和未来真实 Provider 可通过同一接口切换。
- 分析失败返回明确状态和错误信息。
- 过程性指标仍能从分析结果生成，且可追溯。

## 6. 推荐实施顺序

建议顺序：

1. Phase 3.1 报告系统重构
2. Phase 3.2 患者端康复记录纠偏
3. Phase 3.3 角色边界与路由骨架
4. Phase 3.4 治疗师端阶段性评估录入
5. Phase 3.5 能力画像 MVP
6. Phase 3.6 初步自适应训练推荐
7. Phase 3.7 真实分析链路预备

理由：

- 报告系统当前仍有旧评分残留，应该优先与 Phase 2 新评价体系对齐。
- 患者端必须保持低认知负担，专业量表不能放在患者端。
- 阶段性评估录入应由治疗师端承接。
- 能力画像需要稳定的数据输入和清晰角色边界后再做。
- 自适应训练依赖能力画像，不宜提前实现。
- 真实 AI 替换涉及不确定性，适合作为 Phase 3 后段的工程预备或 Phase 4 的正式主题。

## 7. 暂缓事项

以下内容不建议作为 Phase 3 的主线：

- 家属端完整功能：可等患者端报告和能力画像稳定后复用。
- 治疗师端完整工作台：需要更多权限、量表和数据审核设计，先完成阶段评估录入 MVP。
- 真人级数字人、嘴型同步、实时视频：属于产品长期目标，不应抢在训练闭环稳定前实现。
- 长期记忆和实时陪伴对话：需要更完整的隐私、数据结构和对话安全策略。
- 复杂临床量表全流程：当前先保留 WAB/CADL 核心字段和人工录入，避免过早临床化。

## 8. Phase 3 完成定义

Phase 3 完成时，系统应达到：

- 患者端 `/report`、`/evaluation` 与后端评价数据一致，不再以旧综合分作为主线。
- 阶段性评估可以通过治疗师端录入，不依赖 Swagger，也不放在患者端。
- 系统能生成患者当前能力画像。
- 今日训练能根据能力画像给出基础推荐。
- 作答分析结果、过程性指标、报告建议和训练推荐之间有清晰的数据追溯关系。

## 9. 验证建议

每个阶段至少保留以下验证：

- 后端编译：`python -m compileall backend/app`
- 后端导入和 mapper 检查。
- Alembic 当前版本检查。
- 前端构建：`pnpm.cmd run build`
- 接口闭环测试：注册临时 patient、创建智能体、训练、上传录音、分析、查询报告或画像、清理数据。
- 患者端人工流程测试：登录后从首页进入训练、生成反馈、查看 `/evaluation` 和 `/report`。

Phase 3.5 和 Phase 3.6 额外需要构造不同指标组合，验证能力画像和推荐规则确实会变化。
