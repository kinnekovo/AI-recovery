# V3.8 Controlled Active Mode implementation

## Architecture

`PolicyDecision` remains immutable shadow evidence (`mode = shadow` is still enforced by migration `0035_policy_shadow_guard`). V3.8 adds a separate controlled-action layer: `ControlledActionProposal`, `ControlledActionApproval`, `ControlledActionExecution`, `ControlledActionObservation`, append-only audit events, and blocked safety events. There is no global active flag.

## Controlled activation eligibility

`controlled-activation-policy-v1` is the single versioned engineering policy. A proposal requires a shadow decision, its exact policy/rules registry entry in `eligible_for_controlled_activation`, a current non-insufficient Profile V2 snapshot matching the decision, an in-progress owned session, and an allowed action. `suspended`, `validated`, `review_required`, and `insufficient_evidence` cannot pass. Eligibility is checked again immediately before application.

## Proposal lifecycle and therapist approval

The only valid starting transition is `pending_review`. An assigned therapist explicitly approves or rejects it; approval expires within the proposal window. Status transitions are checked in the service. The proposal fingerprint is deterministic for decision, action, target session, mapped before state, and activation-policy version. One effective proposal of a category can exist per patient/session.

## Training integration and adapters

No second training system was added. The adapter only maps to existing `SessionTask` fields in one specified in-progress `TrainingSession`:

- `training_focus_override` promotes an existing task matching the Policy dimension's existing training type to the first order position.
- `difficulty_step_adjustment` changes the first task's existing `prompt_level` by at most one equivalent difficulty step (harder is one fewer prompt; easier is one more prompt), constrained to 0–3.

An unsupported dimension, missing target, incompatible session, or boundary no-op is explicit. The proposal captures the exact current state. A manual change between proposal and apply becomes `state_conflict`; it is never overwritten.

## Execution, rollback, observation, and auditability

Apply is an explicit therapist route, one target session only, and has a unique execution per proposal. It records the minimal before/after field difference and cannot alter profile, assessment, calibration, PolicyDecision, other patients, or other sessions. Rollback is therapist-explicit and restores only fields changed by that execution; it appends audit data rather than deleting history. Observation records an engineering outcome label and optional therapist feedback; it makes no effectiveness claim.

## Safety, authorization, and analytics

Only assigned therapists may create, approve, reject, apply, rollback, or observe. Patients and families never receive routes; unrelated therapists fail assignment checks. Admins have read-only oversight of the history endpoint. All blocked conditions create engineering-level `blocked` safety events before training writes. Analytics reports operational counts/rates and explicitly does not infer clinical validity, safety, or benefit.

## APIs and simulation

Therapist endpoints are under `/api/therapist/patients/{patient_user_id}/policy-v2/`: decision proposal creation, proposal list/detail, approve/reject/apply, execution rollback/observe, and controlled-action history. `python -m app.modules.controlled_policy.simulate --decision <id> --session <id> --action <type>` is read-only and returns eligibility plus mapping; it has no apply option.

## Validation and known limitations

The migration is incremental (`0038_controlled_activation`) after the repository's actual `0037_policy_validation_failures` head and does not alter `0035` or `0036`. Controlled activation is an engineering workflow, not autonomous treatment, a clinical policy, or a therapeutic-effectiveness claim. Existing consent/governance models were not expanded; real deployment still requires the relevant institutional consent and governance review. V3.8 intentionally does not implement autonomous activation, automatic approval, patient/family approval, automatic reassessment, or long-term training-plan rewriting.
