# V3.3 Clinical Stage Implementation

## Implemented

`AssessmentSession` now records instrument identity/version/localization, raw items, subscales, total input, missing items, unit, administration conditions, deviations and comparison metadata. Existing fields and patient APIs remain compatible.

## Canonical contract

`clinical-stage-v2.0` maps only manually supplied source values to `clinical_stage` dimensions. It never computes missing scale scores or cross-scale totals. Missing values are `unavailable/null`; empty data is `unscorable`; unknown instrument version/unit or deviations are `review_required`. Manual intelligibility and acceptability have separate codes.

## Professional API and update policy

Therapist endpoints provide clinical detail, canonical preview, comparison and clinical-source update beneath `/api/therapist/patients/{patient_user_id}/assessments/{assessment_id}/clinical-stage`. Preview uses the production mapper and does not persist. Source update never accepts canonical payloads. Confirmed/adjusted records reject direct update with 409; changes must use review.

## Shadow write and failure isolation

Therapist create and review commit source data first, then invoke the clinical canonical shadow writer. Failures preserve source data and record `evaluation_write_failures`; success adopts the new immutable run and supersedes its predecessor.

## Comparability

The service checks scale/version/locale/localization/unit, missing items, administration mode and protocol deviations. It returns fact-only dimension deltas and machine reason codes; it never reports clinical significance or efficacy. Legacy records lacking metadata are `legacy_insufficient_metadata`.

## Validation and limitations

Targeted clinical tests cover formal/review-required/unscorable mapping, missing-null, separate dimensions, comparability boundaries, source-update finalization policy, shadow failure isolation, professional preview/comparison routing and assignment denial: `9 passed`. Full backend regression: `144 passed`. `alembic current` and `heads` both report the single `0030_clinical_stage_metadata` head; `git diff --check` passes. No proprietary scale rules, version bridge table, patient V3 display, Profile V2 or Policy V2 consumer is implemented.

Empty-database migration remains **environment-blocked**: the configured application account cannot establish the required PostgreSQL administrative connection to create an isolated database, and Docker is installed but its daemon is not running. No development database, password, or Docker configuration was changed. In an environment with create-db permission, run `DATABASE_URL=<temporary-db-url> python -m alembic upgrade head` from `backend`.
