# 言语康复智能体：技术选型说明

## 1. 选型背景

本项目由个人独立开发，目标不是一次性演示页面，而是搭建一个后续可扩展为正式系统的原型。技术选型需要同时满足以下要求：

- 当前开发难度可控
- 支持语音、AI、数字人等能力接入
- 支持患者端、家属端和管理端
- 后续可封装为 App
- 后期可迁移到 Linux 服务器
- 不在第一阶段引入过度复杂的工程体系

---

## 2. 总体技术路线

### 2.1 开发阶段

- 前端：Vue 3 + TypeScript + Vite
- 前端组织：单项目、多角色路由
- 路由：Vue Router
- 状态管理：Pinia
- 网络请求：Axios
- 图表：ECharts
- 后端：Python + FastAPI
- 数据校验：Pydantic
- ORM：SQLAlchemy 2.x
- 数据库迁移：Alembic
- 数据库：PostgreSQL
- 文件存储：本地目录
- AI能力：优先调用外部服务，本地只做轻量音频分析
- 开发环境：Windows 原生
- 前端部署：GitHub Pages
- 暂不引入：Docker、Linux、微服务

### 2.2 后期部署

- 前端继续作为 Web / PWA
- 患者端可通过 Capacitor 封装为 Android / iOS App
- 后端部署到 Linux 云服务器
- PostgreSQL迁移到服务器或云数据库
- 文件迁移到对象存储
- 使用 Docker Compose 管理后端、数据库及相关服务
- 视需要将 ASR、TTS、数字人等高负载模块拆成独立服务

---

## 3. 前端技术选型

### 3.1 核心技术

```text
Vue 3
TypeScript
Vite
Vue Router
Pinia
Axios
ECharts
```

### 3.2 选择 Vue 3 的原因

相比纯 HTML + CSS + JavaScript，Vue 3 更适合本项目这种具有复杂状态变化和多页面流程的系统。

主要优势包括：

- 组件化：智能体卡片、录音按钮、训练卡片、评分卡片等可独立封装
- 响应式：分数、训练状态、当前智能体等数据变化后页面自动更新
- 路由管理：便于区分患者端、家属端和管理端
- 状态管理：适合维护当前用户、当前智能体、训练进度等全局数据
- 后续封装 App 更方便
- 与 ECharts 等可视化工具兼容良好

### 3.3 GitHub Pages 部署

Vue 项目仍然可以部署到 GitHub Pages。

基本流程：

```text
Vue 源码
↓
npm run build
↓
生成 dist
↓
部署到 GitHub Pages
```

需要注意：

- GitHub Pages 只能托管前端静态文件
- FastAPI 和 PostgreSQL 不能运行在 GitHub Pages 上
- 远程试用时，后端需要部署到公网服务器或通过安全方式暴露

## 4. 前端项目组织

第一阶段采用：

> 一个 Vue 项目 + 多角色路由

路由结构：

```text
/login

/patient
├── /home
├── /training
├── /report
└── /agents

/family
├── /dashboard
└── /report

/admin
├── /tasks
└── /users
```

优点：

- 一个仓库
- 一个依赖环境
- 一套构建与部署流程
- 共享登录、请求、类型定义和通用组件
- 适合个人开发
- 后续仍可拆分为独立端

缺点：

- 项目后期会逐渐变大
- 需要做好目录隔离
- 需要使用路由守卫和后端权限校验

---

## 5. 后端技术选型

### 5.1 核心技术

```text
Python
FastAPI
Pydantic
SQLAlchemy 2.x
Alembic
PostgreSQL
```

### 5.2 选择 FastAPI 的原因

- 与 Python AI 生态兼容
- 适合语音处理、ASR、TTS、LLM 等模块
- API 开发效率高
- 自动生成接口文档
- 类型校验清晰
- 便于模块化拆分

### 5.3 模块化单体

第一阶段不采用微服务，而使用模块化单体。

原因：

- 个人开发成本更低
- 部署简单
- 调试更容易
- 仍可通过清晰模块边界为未来拆分预留空间

---

## 6. 数据库选型

### 6.1 选择 PostgreSQL

原因：

- 关系型数据能力强
- 支持 JSONB
- 适合复杂训练记录与评分结果
- 适合未来扩展向量检索和长期记忆
- 后期迁移成本较低

### 6.2 数据库配套

- SQLAlchemy 2.x：ORM
- Alembic：数据库迁移
- psycopg：PostgreSQL 驱动
- Pydantic：接口数据校验

所有数据库结构变化应通过 Alembic 管理，不直接手工修改生产数据库。

---

## 7. 文件存储

开发期采用本地目录：

```text
storage/
├── agent-images/
├── voice-samples/
├── training-audio/
└── generated-audio/
```

数据库中只保存：

- 文件 ID
- 文件类型
- 所属用户
- 存储路径
- 创建时间
- 文件状态

后期迁移到：

- MinIO
- 阿里云 OSS
- 腾讯云 COS
- 其他对象存储

## 8. AI 技术路线

### 8.1 语音识别 ASR

第一阶段优先采用外部服务或轻量模型。

候选：

- FunASR
- Whisper
- 国内云端 ASR 服务

建议通过后端适配层统一调用。

### 8.2 声学分析

本地轻量处理可使用：

- librosa
- openSMILE
- VAD 工具

用于提取：

- 响度 dBA
- 启动时间
- 超过3秒的停顿
- 言语速率
- 有效语音时长
- 基频与稳定性

### 8.3 规则评价与反馈生成

言语康复评价逻辑以 `doc/言语康复评价逻辑开发依据.md` 为准。核心指标优先由 ASR、声学分析与规则层生成，LLM 只用于自然语言反馈生成，不作为 WAB、CADL 等量表数据来源。

输入：

- ASR 文本
- 任务目标
- 脚本目标文本
- 过程性监控规则
- 声学指标

输出结构化 JSON，用于：

- 正确生成的脚本字数百分比
- 错误数
- 言语速率
- 响度
- 改进建议

### 8.4 声音克隆与 TTS

第一阶段不自行训练声音模型。

采用成熟服务：

- 火山引擎
- 阿里云
- 腾讯云
- 其他可用声音复刻服务

系统保存供应商返回的 `voice_id`，后续用于生成训练语音和反馈语音。

### 8.5 数字人

第一版：

```text
头像 + 个性化语音
```

后续逐步加入：

- 2D 动态头像
- 嘴型同步
- 简单表情
- 真人级数字人
- 实时陪伴交互

## 9. 开发环境

第一阶段使用 Windows 原生开发。

建议安装：

- Node.js
- Python
- Conda 或 venv
- PostgreSQL
- VS Code
- Git

暂不要求：

- Docker
- WSL2
- Linux

后期部署或遇到 AI 依赖兼容问题时，再考虑引入 WSL2 或 Docker。

## 11. 关键技术原则

1. 前端不直接调用第三方 AI API。
2. 所有 API 密钥存放在后端环境变量中。
3. 所有核心业务规则放在后端。
4. 外部 AI 服务通过适配器调用。
5. 数据库结构变化通过 Alembic 管理。
6. 第一阶段采用模块化单体，不拆微服务。
7. 文件不直接存入数据库。
8. 录音分析失败时不更新能力画像。
9. 过程性监控规则和参考范围不写死在前端。
10. 后续更换客户端或 AI 供应商时，不影响核心业务逻辑。
