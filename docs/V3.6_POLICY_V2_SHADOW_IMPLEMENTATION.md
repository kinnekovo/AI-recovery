# V3.6 Policy V2 Shadow implementation

## Architecture and input contract

`policy-v2.0` is a new, shadow-only consumer after Profile V2. Its sole profile integration is `get_policy_profile(patient_profile_id)`; it does not query canonical evaluations, assessment raw data, calibration, metric registry, or training records while producing a decision. The contract carries only the Profile V2 snapshot/version metadata and sufficient profile dimensions.

## Rules and explanation

`policy-rules-v1` and `policy-profile-input-policy-v1` are deterministic, E1 engineering observation rules. They do not assert clinical thresholds, diagnoses, efficacy, prognosis, or prescriptions. Falling/mixed/rising/stable profile trends produce explainable focus priority and a shadow-only difficulty action. Profile freshness, coverage, and long clinical-evidence interval can instead gate or signal review. `explain.py` is a deterministic projection of the decision payload, never LLM output.

## Persistence, feedback, and observation

Migration `0034_policy_v2_shadow` adds immutable decision payloads, append-only therapist feedback, actual-training observation links, and retryable failure records. `0035_policy_shadow_guard` enforces the database `mode='shadow'` guard. Decisions use a unique patient/input fingerprint containing profile snapshot and policy/rules versions; repeated input returns the existing decision. Profile/rule changes generate a different fingerprint and preserve history.

Observations link a later real `TrainingSession` and report only `matched`, `not_matched`, or `not_observable` for focus/difficulty/reassessment. They never score therapist correctness or modify a session. Feedback is append-only with therapist-specific review rounds.

## Professional APIs and safety

All endpoints remain under the existing therapist-patient assignment guard:

- `POST /api/therapist/patients/{id}/policy-v2/shadow`
- latest/history/detail/explanation reads
- append-only feedback and explicit observation
- analytics distribution read

No patient or family route is added. No new router or service writes `TrainingSession`, task template, plan, session ordering, assessment schedule, legacy recommendation, or phase4.3 state. The legacy policy remains `phase4.3-historical-r0-frozen`.

Offline generation: `python -m app.modules.policy_v2.run --patient <id>` or `--from-profile <snapshot-id>`. Both use the same shadow service and cannot activate policy.

## Analytics

The service reports decision count plus focus, difficulty, reassessment, therapist-agreement, and shadow-vs-actual distributions. Missing feedback is omitted, never treated as disagreement; no “accuracy” is calculated.

## Validation

- Baseline immediately before V3.6 development was the existing suite result of **162 passed**.
- Added `tests/test_policy_v2_engine.py`: 13 deterministic rule/explanation cases, plus `tests/test_policy_v2_shadow_safety.py`: 2 persistence/idempotency and legacy-input non-mutation cases.
- Final full suite: **177 passed**.
- Development DB upgraded through `0035_policy_shadow_guard (head)`; `alembic heads` has one head.
- `git diff --check` passed (CRLF conversion warnings only).

The initial `0035` attempt found that this development database already had the shadow check constraint because 0034 was first applied while it was being authored. 0035 conditionally detects that constraint, so both this historical development DB and a clean 0034→0035 upgrade are supported. A temporary empty PostgreSQL/Docker validation remains environment-blocked as previously documented.

## Known limitations

V3.6 intentionally excludes active mode, automatic training changes, autonomous therapy, reassessment scheduling, RL/bandits/learned recommendation, diagnosis, prescription, efficacy conclusions, and patient/family presentation. Policy failure persistence is isolated from Profile/Training/Assessment operations. Future promotion requires a separately versioned and professionally governed workflow.
