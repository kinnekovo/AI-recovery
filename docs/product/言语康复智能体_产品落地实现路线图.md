# 言语康复智能体：从当前阶段到可用 Web 产品的落地实现路线图

日期：2026-09-02

## 一、文档目的

这份文档用于确认：当前项目从已有 MVP 阶段继续推进，最终如何成为一个可供患者真实使用的 Web 产品。

它不是单个功能的开发文档，也不是重新写一份 PRD，而是连接“现在已经做到哪里”和“最终如何上线使用”的产品实现路线图。

本文回答四个问题：

1. 当前系统已经完成了什么。
2. 最终可用 Web 产品应该具备哪些能力。
3. 从当前阶段到最终产品，需要分哪些阶段推进。
4. 每个阶段具体要实现什么、如何验收、哪些事情暂时不做。

## 二、当前项目状态

当前系统已经不再是空白原型，而是一个已经跑通主要业务闭环的 Web MVP。

当前已完成的核心能力包括：

- 患者注册、登录和身份鉴权。
- 患者创建个性化陪伴智能体。
- 上传智能体头像和声音样本。
- 声音克隆 Provider 预留。
- Mock TTS 欢迎语生成。
- 患者端训练入口、训练会话、录音上传。
- 跟读训练与场景表达训练。
- 作答 Attempt 记录。
- ASR、声学分析、LLM 反馈 Provider 预留。
- 基于过程性监控的训练反馈。
- 过程性指标写入和趋势查看。
- 能力画像 MVP。
- 推荐任务组、自适应推荐和趋势归因。
- 家属端训练趋势和陪伴提醒。
- 治疗师端患者列表、训练记录、趋势、阶段性评估和自然语言调整入口。
- Avatar Runtime 抽象。
- 患者端数字人陪练入口和训练会话陪练状态。

当前最新阶段可以概括为：

```text
患者训练闭环已经成立，三端雏形已经具备，数字人陪练已进入患者端训练体验。
```

当前仍然不足以作为真实患者长期使用产品的原因：

- 真实 TTS、声音克隆和 LLM 反馈仍未形成稳定生产链路。
- 部分 ASR 和声学能力虽已预留或局部接入，但还需要质量控制和失败处理。
- 数字人目前是默认 2D 状态陪练，还不是完整个性化语音陪练。
- 报告还偏页面展示，缺少正式导出和留档能力。
- 缺少真实试用质控看板。
- 缺少完整隐私、授权撤回、数据保留和账号管理流程。
- 缺少患者真实使用场景下的低认知负担细节打磨。
- 缺少上线部署、备份、日志、监控和异常告警方案。

## 三、最终 Web 产品定义

最终产品不是一个简单“语音打分网页”，而是一个面向脑卒中后言语障碍患者的陪伴式康复训练 Web 产品。

最终产品应满足：

```text
患者能在家中独立或在家属辅助下完成每日言语训练；
系统能使用患者授权的熟悉形象和声音进行陪伴引导；
每次训练录音、分析、反馈和趋势都可追溯；
治疗师能查看训练表现并给出方向性调整；
家属能理解患者是否坚持训练、最近是否稳定；
系统在真实服务失败或录音质量差时仍可恢复；
数据、授权、隐私和访问权限符合真实使用要求。
```

## 四、目标用户与产品边界

### 4.1 患者端

患者端是产品核心。

患者端必须做到：

- 首次进入时能清楚完成注册、登录和智能体创建。
- 能在家属辅助下上传头像和声音样本。
- 能理解授权范围，不被复杂术语干扰。
- 能看到当前陪伴智能体。
- 能一键开始今日训练。
- 能听到数字人的任务说明和示范。
- 能完成录音、试听、上传和查看反馈。
- 能看到简洁的训练记录和趋势。
- 能收到积极、克制、可执行的建议。

患者端不应该做：

- 展示复杂临床量表细节。
- 展示模型供应商、置信度、内部评分配置。
- 让患者决定训练算法参数。
- 用诊断语气告诉患者病情好坏。
- 因 AI 服务失败让患者卡死在页面上。

### 4.2 家属端

家属端是陪伴和观察入口。

家属端必须做到：

- 绑定患者。
- 查看患者今日是否训练。
- 查看训练坚持情况。
- 查看最近趋势是否稳定。
- 查看系统给出的陪伴建议。
- 必要时协助患者创建或维护智能体。

家属端不应该做：

- 修改治疗策略。
- 修改评分结果。
- 直接参与模型评价。
- 查看不适合家属理解的内部技术字段。

### 4.3 治疗师端

治疗师端是专业观察和策略调整入口。

治疗师端必须做到：

- 查看患者列表。
- 查看单次训练记录、录音、转写和过程指标。
- 查看趋势与推荐归因。
- 录入或复核阶段性评估。
- 用自然语言补充下一阶段训练方向。
- 导出阶段性报告。

治疗师端不应该回到“每条推荐都审批”的繁重流程。

推荐主路径应是：

```text
系统根据能力画像和趋势生成训练建议
-> 治疗师查看趋势和证据
-> 必要时补充方向性意见
-> 系统下次推荐时纳入治疗师意见
```

### 4.4 管理端

管理端用于产品运营和试用管理。

正式产品需要管理端，但当前可以晚于患者端、家属端、治疗师端核心链路。

管理端应包括：

- 用户管理。
- 患者/家属/治疗师关系管理。
- 题库管理。
- 训练任务模板管理。
- Provider 配置状态查看。
- 试用质控看板。
- 系统错误和失败任务查看。
- 数据导出。

## 五、核心产品闭环

最终产品必须围绕一个稳定闭环展开：

```text
创建智能体
-> 初始评估
-> 生成能力画像
-> 推荐今日训练
-> 数字人陪练
-> 患者录音
-> ASR 与声学分析
-> 过程性监控反馈
-> 更新训练记录与能力画像
-> 治疗师/家属查看趋势
-> 下一次推荐调整
```

所有功能都应该服务这个闭环。不能服务这个闭环的功能，应推迟。

## 六、产品实现总阶段

从当前阶段到真实可用 Web 产品，建议分为七个阶段。

```text
阶段 A：当前 MVP 稳定化
阶段 B：个性化数字人语音闭环
阶段 C：真实语音分析闭环
阶段 D：报告、试用和质控闭环
阶段 E：隐私、安全和权限闭环
阶段 F：部署、监控和运维闭环
阶段 G：真实患者试用与产品打磨
```

## 七、阶段 A：当前 MVP 稳定化

### 目标

把当前已经实现的功能整理成稳定、可演示、可继续迭代的基础版本。

### 需要实现

1. 梳理当前患者端、家属端、治疗师端所有页面。
2. 确认注册登录、创建智能体、训练、录音、分析、报告链路能跑通。
3. 清理已经废弃但仍可能被页面误用的旧接口。
4. 统一前端错误提示。
5. 统一后端接口响应。
6. 补齐 `.env.example`。
7. 补齐启动说明。
8. 确认数据库迁移从 0001 到最新版本可顺序执行。
9. 确认 mock 模式下不依赖外部服务。

### 验收标准

- 新开发者按文档可以启动前后端。
- 没有真实 AI key 时，系统仍可完成完整演示。
- 患者至少能完成一组训练并看到反馈。
- 家属端和治疗师端能看到训练记录或趋势。
- 当前阶段功能说明与代码实际一致。

### 不做

- 不急着接更多模型。
- 不重做页面视觉风格。
- 不拆微服务。
- 不引入复杂任务队列。

## 八、阶段 B：个性化数字人语音闭环

### 目标

让数字人真正进入患者训练体验，并优先使用当前智能体的声音进行训练引导。

当前 Phase 6.1-6.2 已经完成 Avatar Runtime 和患者端陪练界面，下一步是补齐语音生成链路。

### 需要实现

1. 后端新增训练口播 TTS 接口。
2. 训练入口说明、任务示范、下一题引导、完成鼓励都能生成音频。
3. 生成音频保存为 `generated_audio` 文件资产。
4. 前端 Avatar Runtime 优先播放后端生成音频。
5. 音频生成失败时 fallback 到浏览器 TTS。
6. 患者开始录音时自动停止数字人口播。
7. 数字人状态保持：
   - idle：等待
   - speaking：示范或说明
   - listening：患者录音
   - thinking：上传分析
   - encouraging：完成鼓励
   - error：失败提示

### 后端实现方向

复用现有结构：

```text
backend/app/integrations/tts/provider.py
backend/app/modules/files/
backend/app/modules/training/
```

建议接口：

```text
POST /api/training/avatar-speech
```

响应返回：

```json
{
  "text": "请跟我说这一句：今天天气很好。",
  "audio_url": "/api/files/{file_id}/content",
  "provider": "mock",
  "fallback": false
}
```

### 前端实现方向

复用现有：

```text
frontend/src/composables/useAvatarRuntime.ts
frontend/src/avatar/providers/static2d.ts
frontend/src/views/patient/TrainingView.vue
frontend/src/views/patient/TrainingSessionView.vue
```

核心策略：

```text
先请求后端生成音频
-> 成功则 avatar.speak(text, audio_url)
-> 失败则 avatar.speak(text)
```

### 验收标准

- 点击“听数字人说明”可以播放后端生成的音频。
- 进入训练会话后，数字人可以朗读当前任务。
- 录音时数字人停止说话。
- TTS 失败时训练仍可继续。
- 不改变评分、推荐和报告接口。

## 九、阶段 C：真实语音分析闭环

### 目标

让真实患者录音进入系统，并稳定生成可解释、可追溯的过程性监控结果。

### 需要实现

1. 真实 ASR Provider 稳定接入。
2. 本地或外部声学分析稳定接入。
3. 音频质量检测。
4. 低质量录音提示。
5. 评分结果映射到稳定指标。
6. LLM 只用于自然语言反馈，不作为量表事实来源。
7. Provider 失败时 fallback 或明确失败。

### 过程性监控指标

单次训练核心指标保持：

```text
script_accuracy
error_count
speech_rate
loudness
```

可以逐步增加：

```text
speaking_duration_seconds
long_pause_over_3s_count
quality_status
quality_reason
asr_confidence
provider_name
provider_version
```

### 音频质量规则

至少需要识别：

- 录音太短。
- 声音太轻。
- 长时间静音。
- 文件无法解析。
- ASR 失败。
- 声学分析失败。

患者端提示示例：

```text
这次录音声音有点轻，可以离麦克风近一点再试一次。
```

治疗师端提示示例：

```text
本次结果受录音质量影响，不建议用于能力趋势判断。
```

### 验收标准

- 上传真实中文录音后可获得真实转写。
- 声学分析能产出语速、响度、停顿等指标。
- 低质量录音不会误更新能力画像。
- 患者端反馈简短可执行。
- 治疗师端能看到转写、录音、过程指标和质量状态。

## 十、阶段 D：报告、试用和质控闭环

### 目标

让系统不仅能训练，还能用于真实试用、阶段汇报和证据留存。

### 需要实现

1. 患者端简化报告。
2. 家属端陪伴观察报告。
3. 治疗师端正式阶段报告。
4. PDF 或可打印报告导出。
5. 试用质控看板。
6. 训练数据导出。

### 报告内容

治疗师报告应包括：

- 患者基本信息。
- 训练时间范围。
- 训练次数。
- 推荐任务完成情况。
- 过程性指标趋势。
- 低质量录音比例。
- 阶段性评估结果。
- 治疗师备注。
- 下一阶段建议。

患者报告应包括：

- 最近练了几次。
- 哪些地方比较稳定。
- 下一次重点练什么。
- 鼓励性总结。

家属报告应包括：

- 是否坚持训练。
- 最近状态是否稳定。
- 家属可以怎么陪伴。
- 不展示复杂医学细节。

### 试用质控看板

管理端或治疗师端应能看到：

- 训练完成率。
- 推荐任务完成率。
- 录音失败率。
- 低质量录音比例。
- ASR 失败次数。
- 声学分析失败次数。
- TTS 失败次数。
- 患者活跃天数。
- 家属查看次数。
- 治疗师查看次数。

### 验收标准

- 能导出某位患者某时间段报告。
- 报告中的指标与页面展示一致。
- 能判断试用问题来自患者未训练、录音质量差还是 Provider 失败。
- 项目汇报时可以直接使用报告和质控截图。

## 十一、阶段 E：隐私、安全和权限闭环

### 目标

让系统具备真实患者使用所需的数据安全、授权和权限边界。

### 需要实现

1. 声音和形象授权版本化。
2. 授权撤回。
3. 撤回后禁止继续生成新语音或新形象内容。
4. 文件访问鉴权。
5. 家属-患者绑定确认。
6. 治疗师-患者关系绑定。
7. 管理员操作审计。
8. 敏感字段日志脱敏。
9. 数据删除或停用策略。

### 关键规则

- 患者只能访问自己的训练记录。
- 家属只能访问已绑定患者的陪伴观察信息。
- 治疗师只能访问被分配或绑定的患者。
- 管理员不能绕过授权生成声音克隆内容。
- 撤回授权后，历史训练记录可以保留，但不能继续生成新陪伴语音。

### 验收标准

- 未授权用户无法访问他人文件。
- 家属解绑后无法继续查看患者训练数据。
- 授权撤回后，TTS/声音克隆相关接口拒绝新生成。
- 日志中不出现 API key、完整 token、敏感原始 payload。

## 十二、阶段 F：部署、监控和运维闭环

### 目标

让系统从本地开发项目变成可部署、可维护、可恢复的 Web 产品。

### 需要实现

1. 生产环境配置。
2. 前端构建和静态资源部署。
3. 后端服务部署。
4. PostgreSQL 生产数据库。
5. 文件存储策略。
6. 数据库备份。
7. 日志收集。
8. 错误监控。
9. Provider 调用监控。
10. 健康检查接口。

### 推荐部署演进

第一步可以使用：

```text
单机部署
Nginx
FastAPI
PostgreSQL
本地或挂载磁盘文件存储
```

后续再演进到：

```text
对象存储
Redis/Celery
Docker Compose
云服务器
CDN
独立备份策略
```

### 必要环境变量

应整理：

```env
DATABASE_URL=
SECRET_KEY=
BACKEND_CORS_ORIGINS=
STORAGE_ROOT=

ASR_PROVIDER=
ASR_API_KEY=
ASR_BASE_URL=

ACOUSTIC_PROVIDER=
ACOUSTIC_API_KEY=
ACOUSTIC_BASE_URL=

TTS_PROVIDER=
TTS_API_KEY=
TTS_BASE_URL=
TTS_MODEL=

LLM_FEEDBACK_PROVIDER=
LLM_FEEDBACK_API_KEY=
LLM_FEEDBACK_BASE_URL=
LLM_FEEDBACK_MODEL=
```

### 验收标准

- 新环境可以按文档部署。
- 数据库迁移可执行。
- 前端能访问后端。
- 文件上传、下载和播放正常。
- 服务重启后训练记录不丢失。
- Provider 失败可被定位。

## 十三、阶段 G：真实患者试用与产品打磨

### 目标

进入小规模真实试用，根据患者、家属和治疗师反馈打磨产品。

### 试用前准备

至少准备：

- 试用说明。
- 授权说明。
- 账号创建流程。
- 患者使用手册。
- 家属使用手册。
- 治疗师查看说明。
- 问题反馈表。
- 数据导出方案。
- 紧急停止或账号停用方案。

### 试用范围建议

第一轮试用不宜追求人数多。

建议：

```text
3-5 位患者
1-2 位治疗师
每位患者试用 1-2 周
每天 5-10 分钟训练
```

重点观察：

- 患者是否能完成训练。
- 是否愿意重复使用。
- 数字人陪伴是否有帮助。
- 录音质量是否足够稳定。
- 治疗师是否能理解系统输出。
- 家属是否能看懂趋势和提醒。

### 打磨方向

根据试用反馈重点优化：

- 页面操作路径。
- 按钮大小和文案。
- 录音开始/结束反馈。
- 低质量录音提示。
- 训练任务长度。
- 数字人口播节奏。
- 反馈文本是否过长。
- 患者是否理解“今天为什么练这个”。

### 验收标准

- 患者能在少量辅助下完成训练。
- 家属能看懂陪伴观察页。
- 治疗师认为趋势和报告有参考价值。
- 系统能稳定保存试用数据。

## 十五、推荐实施顺序

从当前阶段继续推进，建议优先级如下：

1. 先做 Phase A：稳定当前 MVP，确认所有已有链路能跑。
2. 再做 Phase B：补齐数字人语音闭环，让产品特色真正进入训练。
3. 再做 Phase C：真实语音分析闭环，让训练数据可信。
4. 再做 Phase D：报告和质控，用于试用和汇报。
5. 再做 Phase E：隐私、安全、权限，进入真实使用前必须补齐。
6. 再做 Phase F：部署和运维，准备外部访问。
7. 最后做 Phase G：小规模真实患者试用和产品打磨。

如果时间有限，最小可试用版本必须完成：

```text
Phase A + Phase B + Phase C 的核心链路 + Phase E 的基础权限与授权
```

如果要用于项目展示或结项，建议至少完成：

```text
Phase A + Phase B + Phase C + Phase D
```

如果要给真实患者长期使用，必须完成：

```text
Phase A 到 Phase F，并完成至少一轮 Phase G 小规模试用
```

## 十六、当前最应该做的下一步

## 十七、不建议现在做的事

当前阶段不建议：

- 直接做真人级视频数字人。
- 直接做长期聊天记忆。
- 直接训练个性化模型。
- 直接拆成微服务。
- 大规模重构前端 UI。
- 把治疗师端做成复杂审批后台。
- 在没有真实试用数据前过度优化推荐算法。
- 让 LLM 自动生成临床量表结果。

这些功能并不是没价值，而是现在做会把主闭环拖散。

当前产品的主线应该始终是：

```text
患者愿意练

-> 数据可信
-> 反馈可懂
-> 治疗师可看
-> 家属可陪
-> 系统可持续运行
```
