# 言语康复智能体 Product Design v1.0

> 文档定位：新版产品总设计文档。用于统一产品目标、用户角色、核心流程、数据对象、AI 能力边界与 MVP 范围，并作为后续 UI/Interaction Spec、技术设计和 Codex 开发 Prompt 的上游规格。
>
> 版本：v1.0
> 日期：2026-09-20

---

## 1. 产品定位

### 1.1 一句话定义

言语康复智能体是一个**面向居家言语康复的 AI 训练与治疗师协作系统**。

患者按照个性化训练计划完成日常训练，获得即时、易理解的反馈并看到自己的长期变化；治疗师无需逐条检查所有训练记录，而是由系统汇总患者状态、筛出值得关注的问题，并基于结构化证据调整下一阶段训练方案。

### 1.2 产品核心价值

患者侧核心价值：

- 每天知道“今天练什么、为什么练、要练多久”。
- 可以独立完成居家训练，卡住时获得渐进式帮助。
- 每次训练后得到简短、可行动的反馈。
- 能够看到自己持续发生的变化，而不是只看到抽象分数。
- 能感受到治疗师持续参与，而不是对着 AI 单独刷题。

治疗师侧核心价值：

- 不再逐条审核正常训练记录。
- 每天优先看到“哪些患者值得关注、为什么”。
- 能快速理解患者最近发生了什么变化。
- 可以追溯 AI 结论背后的音频、转写、指标和训练记录。
- 可以基于系统整理的证据调整训练目标、难度和策略，并让修改自动作用于患者后续训练。

### 1.3 第一版目标用户

MVP 优先服务：

- 已具备一定口语表达能力、能够完成居家训练的脑卒中后言语康复患者。
- 负责制定康复目标、阶段训练重点和复查计划的治疗师。

MVP 不追求一次覆盖所有失语症、构音障碍、言语失用等情况；第一版优先做好跟读、短句表达、场景表达和简单连续对话。

### 1.4 产品边界

系统不是自动诊断工具，也不是 AI 自主康复师。

AI 可以生成训练内容、进行语音识别、分析训练表现、解释趋势并提出建议；正式康复目标、阶段调整、量表结果确认和长期计划修改必须保留明确的专业控制边界。

## 2. 产品核心闭环

整个产品围绕以下闭环设计：

**治疗师制定目标 → 患者训练 → AI 即时反馈 → 系统持续观察 → 系统筛选值得关注的问题 → 治疗师判断 → 调整训练方案 → 下一次训练自动变化**

产品设计必须始终服务这条主链。无法明显服务主链的功能，不进入 MVP。

---

## 3. 产品设计原则

1. **训练优先于数据**：患者进入系统首先是为了完成训练，而不是查看仪表盘。
2. **变化优先于绝对分数**：患者更需要知道“比之前更完整”“提示更少”，而不是单独看到 80 分、95%。
3. **异常优先于流水账**：治疗师工作台优先展示真正值得关注的问题，而不是所有记录。
4. **结论必须可追溯证据**：治疗师能够从 Observation 回溯到 Metric，再回溯到音频、转写、题目、提示记录或正式量表。
5. **每个评估最终都要连接行动**：评估结果要么改变后续训练，要么帮助治疗师决策，否则不应该占据产品中心。
6. **患者看结论和行动，治疗师看证据和专业指标**：两端信息可见性不对称。
7. **事实、解释、建议必须分层**：测量结果不能与 AI 解释或建议混为一谈。
8. **正式计划由治疗师控制，训练内微调可自动完成**。
9. **LLM 是解释层，不是事实层**。
10. **没有可靠结果就没有结果**：识别失败、噪声过大、量表未施测时，不猜值、不补值、不伪造趋势。

## 4. 用户角色

### 4.1 患者

患者使用系统时只需持续回答三个问题：

- 今天练什么？
- 我刚才练得怎么样？
- 我最近有没有进步？

患者不需要理解 clinical stage、comparability、WAB 版本、ASR confidence 等系统内部概念。

### 4.2 治疗师

治疗师每天打开系统主要回答四个问题：

- 今天有哪些患者值得我关注？
- 为什么值得关注？
- 患者最近发生了什么变化？
- 我要不要调整下一阶段训练？

### 4.3 管理员

管理员退到真正的后台角色，负责：

- 用户与角色管理。
- 系统与模型配置。
- 训练内容模板或题库管理。
- 运行状态与系统审计。

管理员式交互不得混入治疗师主流程。

## 5. 患者端完整用户旅程

### 5.1 首次使用

首次使用不直接进入 Dashboard，而进入一次性 Onboarding：

欢迎说明 → 基础建档 → 简短初测 → 生成第一版训练重点 → 告诉患者“接下来练什么、为什么练” → 进入首页。

初测结果不以专业指标报告为中心，而以患者可理解的总结呈现，例如：

> 目前你能比较清楚地表达简单需求。连续说较长的句子时容易停顿。接下来我们会先练习把一句话完整、连续地说出来。

### 5.2 日常训练

患者日常流程：

首页 → 今日训练 → 训练准备 → 逐题练习 → 即时反馈 → 分级提示 → 组间总结 → 今日总结 → 进展积累。

### 5.3 两周后的阶段体验

完成一段时间训练后，患者在“我的进展”中看到：

- 近期变化。
- 需要提示的变化。
- 训练里程碑。
- 阶段回顾。
- 治疗师对下一阶段训练的调整。

患者应清楚感受到“我的训练有人持续看，而且后续内容会根据我的情况变化”。

## 6. 患者端信息架构

一级导航固定为：

**首页｜训练｜我的进展｜我的**

首次建档/初测属于 Onboarding，不占长期一级导航。

### 6.1 首页

首页只负责回答：**今天做什么？**

必须包含：

- 问候与当前训练重点。
- 今日训练预计时长。
- 今日训练结构。
- 今日训练重点。
- 一个最强主按钮：开始/继续今天的训练。
- 轻量的最近变化。
- 如治疗师刚调整计划，则一次性显示计划更新说明。

首页不展示：

- ASR 置信度。
- dBFS 等技术指标。
- CADL/WAB 专业量表结果。
- clinical stage / assessment session 等内部术语。

### 6.2 训练

训练页面是连续训练空间，不是题库或历史记录页。

状态流程：

训练准备 → 做题 → 录音 → 反馈 → 提示/重试 → 下一题 → 组间总结 → 今日总结。

核心原则：

- 单题反馈只解决“下一次该怎么说”。
- 分级提示由轻到重，不直接给完整答案。
- 使用大点击区域、固定按钮位置、大字号。
- 训练中尽量隐藏复杂导航。
- 支持中途退出与继续训练。
- 正式训练完成后，额外复习不能重复计入正式指标。

### 6.3 我的进展

负责回答：**我到底有没有变好？**

核心模块：

- 最近两周自然语言总结。
- 表达完整、提示依赖、连续表达等患者可理解维度。
- 简单趋势图。
- 康复里程碑。
- 阶段回顾与治疗师新计划。

不鼓励患者侧大量展示抽象 0-100 分。

### 6.4 我的

只负责：**这个产品怎样适合我。**

主要内容：

- 我的康复计划。
- 陪伴设置（形象、声音、称呼等）。
- 使用辅助：字号、朗读、自动播放、等待时间、简化页面。
- 训练提醒。
- 个人资料。
- 隐私与数据。
- 帮助与反馈。
- 退出登录。

“我的智能体”不作为一级导航，而作为全产品交互人格存在。

## 7. 患者端关键状态与异常处理

患者端必须覆盖以下状态：

- onboarding_required：首次使用。
- waiting_for_plan：尚无正式训练计划。
- ready_to_train：今日可训练。
- in_progress：训练进行中。
- paused：训练暂停，可继续。
- completed：今日正式训练已完成。
- progress_accumulating：数据不足，趋势尚未形成。
- stage_review_pending：治疗师正在回顾近期情况。
- plan_updated：治疗师已更新后续训练。

关键异常策略：

- 麦克风权限不足：清晰解释原因并引导开启。
- 无声音：训练前先做轻量检测。
- 训练中退出：自动保存已完成内容。
- 网络异常：不丢失已录制结果，必要时允许稍后继续。
- ASR 不确定：显示“没有听清楚”，不得判患者表达错误。
- 连续识别失败：允许跳过，不计入能力下降。
- 患者卡住：触发分级提示；最高提示后仍未完成则允许结束该题。
- LLM 总结失败：使用模板降级，不阻断训练闭环。
- 数据不足：不强行画趋势。
- 单次下降：不直接告知“能力退步”。
- 治疗师正在复查：不阻止患者继续当前已发布训练。

## 8. 治疗师端产品定位与信息架构

治疗师端是：**患者变化监测 + 康复计划决策工作台。**

一级导航：

**工作台｜患者｜训练方案**

系统设置、账号等进入次级菜单。

### 8.1 工作台

负责回答：**今天谁需要我关注，为什么？**

核心模块：

- 今日待关注患者数量。
- 按类型归类：阶段回顾、训练困难、患者主动求助、依从性问题、数据异常等。
- 每个 AttentionItem 必须明确触发原因。
- 近期患者概览。

不得回到“所有记录都待审核”的模式。

### 8.2 患者工作空间

点入单个患者后，治疗师看到：

- 患者概览。
- 当前康复目标与阶段训练重点。
- 最近 7 天完成情况。
- 近期变化。
- 系统需要关注的事项。
- 当前训练计划。
- 训练历程。
- 阶段回顾。
- 专业评估。

第一屏优先回答：

- 现在在练什么？
- 最近发生了什么变化？
- 有没有需要我处理的问题？
- 当前计划要不要改？

### 8.3 单次训练详情

治疗师进入某次训练后，必须看到完整专业信息。

页面结构：

1. 本次训练概览。
2. 训练证据。
3. 专业指标。
4. 指标来源与可靠性。
5. 历史可比趋势。
6. 系统观察与建议。
7. 治疗师决策。

必须保留的专业指标包括：

- 接受度。
- CADL 总分。
- 错误次数。
- 声音响度。
- 表达完整度。
- 言语速率。
- WAB 可靠度。
- WAB 流利性。
- WAB 语法。
- WAB 信息量。
- WAB 复述可懂度。
- WAB 语序。

同时必须明确区分：

- 本次训练测得。
- 最近一次正式评估。
- 本次未施测。

未实际施测的专业量表值不得显示为 0、空值或 AI 猜测结果。

### 8.4 训练方案

训练计划采用四层结构：

1. Rehabilitation Goal：长期康复目标。
2. Stage Focus：当前阶段训练重点。
3. Training Strategy：频率、形式、难度、信息单元、提示策略等。
4. Daily Exercise Content：每日具体训练内容。

治疗师主要控制前三层；AI 主要负责第四层，并可在第三层允许范围内做 Session 内临时适应。

正式计划必须版本化，例如：Plan v1 → Stage Review → Plan v2。

### 8.5 阶段回顾

Stage Review 是决策节点，不是单纯报告。

输入：

- 当前 TrainingPlan。
- 阶段内 TrainingSessions。
- 可比较 Metrics。
- 正式 Assessments。
- Observations。
- AttentionItems。
- 治疗师备注。

系统输出：

- 本阶段发生了什么。
- 哪些变化有证据支持。
- 哪些数据不可直接比较。
- 系统建议。

治疗师最终选择：

- 继续当前计划。
- 调整当前阶段重点。
- 进入下一阶段。
- 增加正式评估。

只有治疗师确认后才形成新的 TrainingPlan 版本。

## 9. 事实、解释、建议三层语义

### 9.1 Fact / Metric

可追溯的事实，例如：

- 完成 8/10 题。
- 使用 Level 2 提示。
- 语速 112 字/min。
- CADL 总分 74。

### 9.2 Observation

对事实的归纳，例如：

- 最近几次训练中提示使用减少。
- 连续表达长句时停顿较多。

### 9.3 Recommendation

基于事实和观察给出的候选建议，例如：

- 可考虑继续保持当前难度。
- 可考虑增加两轮场景对话练习。

治疗师 UI 必须清楚区分：

**测量结果 / 系统观察 / 系统建议**

---

## 10. 指标体系与指标字典原则

### 10.1 日常训练指标

包括：

- 错误次数。
- 声音响度。
- 表达完整度。
- 言语速率。
- 提示等级与提示次数。
- 训练完成率。
- 独立完成情况。

特点：

- 每次训练可能产生。
- 可用于短期趋势。
- 多数可自动计算。
- 患者看自然语言翻译，治疗师看原始值与来源。

### 10.2 专业量表 / 临床评估指标

包括：

- CADL 总分。
- WAB 可靠度。
- WAB 流利性。
- WAB 语法。
- WAB 信息量。
- WAB 复述可懂度。
- WAB 语序。

每项至少绑定：

- 测量时间。
- 量表名称与版本。
- 施测方式。
- 数据来源。
- 是否完整施测。
- 评分者。
- 流程偏离。
- 是否可与历史直接比较。

### 10.3 依从与行为指标

包括：

- 本周完成次数。
- 计划完成率。
- 平均训练时长。
- 连续未训练天数。
- 主动求助次数。

依从性不能直接等价为康复效果。

### 10.4 衍生趋势指标

例如：

- 提示依赖减少。
- 表达完整性稳定。
- 长句表现波动增加。

只能基于可比较数据生成。

---

## 11. Comparability 原则

趋势分析必须严格拆成三步：

1. **Comparability Engine**：判断哪些记录可比较。
2. **Trend Engine**：对可比数据做确定性计算。
3. **LLM Explanation**：把趋势翻译成人能理解的语言。

禁止将明显不同任务结构、难度、施测方式或数据质量的结果直接画在同一趋势线上。

若不可比较，UI 应显示：

> 暂不直接比较。本次训练方式与之前不同，但仍可查看各次原始结果。

---

## 12. 治疗师待关注事项 AttentionItem

AttentionItem 表示：**系统认为值得治疗师看一下的事情**，不是临床结论。

MVP 允许以下触发来源：

- 连续多次在可比训练中出现明显困难。
- 提示依赖持续增加。
- 多次无法完成同一训练目标。
- 患者主动“想告诉治疗师”。
- 连续未按计划完成训练。
- 数据存在明显冲突或置信度不足。
- 到达阶段回顾时间。

单次指标波动不得轻易触发 AttentionItem。

处理结果可以是：

- 无需处理。
- 添加临床备注。
- 调整训练计划。
- 加入阶段回顾。

## 13. 核心数据对象

系统核心对象：

- Patient
- Therapist
- RehabilitationGoal
- TrainingPlan
- TrainingSession
- Exercise
- ExerciseAttempt
- Metric
- Evidence
- Observation
- Recommendation
- AttentionItem
- Assessment
- StageReview
- TherapistDecision
- Milestone

### 13.1 主关系

Patient
→ RehabilitationGoal
→ TrainingPlan
→ TrainingSession
→ ExerciseAttempt
→ Evidence
→ Metric
→ Observation
→ Recommendation / AttentionItem
→ StageReview
→ TherapistDecision
→ 新 TrainingPlan

### 13.2 TrainingPlan

TrainingPlan 是系统真正的核心对象。

必须版本化并记录生效时间，以保证能够回答：

> 患者当时为什么练这些内容？

### 13.3 TrainingSession 与 ExerciseAttempt

TrainingSession 表示一次完整训练。

ExerciseAttempt 表示一次具体作答。

Session 负责“今天发生了什么”；Attempt 负责“某一道题具体发生了什么”。

### 13.4 Evidence

Evidence 支撑指标与结论，包括：

- 原始音频。
- ASR 转写。
- 音频时间段。
- 提示记录。
- 题目与任务难度。
- 治疗师评分。
- 量表原始记录。

### 13.5 Assessment

Assessment 只指正式专业评估或量表施测，不等同于日常训练评价。

### 13.6 Milestone

用于患者可理解的康复里程碑，例如：

- 第一次无需提示完成点餐表达。
- 第一次完成两轮对话。
- 连续三次独立完成简单需求表达。

Milestone 应由确定事实触发，LLM 只负责自然语言表达。

## 14. AI 决策边界

统一原则：

**规则负责保证系统稳定与安全，AI 负责理解与建议，治疗师负责正式临床决策，患者负责训练过程中的自主选择。**

### 14.1 AI 可以自动执行

- 在 TrainingPlan 边界内生成每日 Exercise。
- ASR 转写。
- 声学指标计算。
- 单题 Observation。
- 患者即时反馈。
- Session 内提示与轻度难度适应。
- Session 总结。
- 对可比较趋势做自然语言解释。
- AttentionItem 的事实摘要。
- 阶段回顾的候选建议。
- 治疗师计划修改候选方案。
- 陪伴式语言与 TTS 表达。

### 14.2 AI 不得自动执行

- 独立确定长期康复目标。
- 自动改变正式阶段训练重点。
- 自动进入下一康复阶段。
- 猜测 CADL / WAB 正式评分。
- 覆盖事实层数据。
- 直接发布新的正式 TrainingPlan。
- 将单次训练异常解释为患者能力恶化。

## 15. AI Capability Contract

### 15.1 训练内容生成

输入：TrainingPlan、阶段重点、训练类型、难度边界、场景、提示策略。

输出：结构化 Exercise。

降级：预置题库/模板。

### 15.2 ASR

输入：音频。

输出：转写、时间信息、置信状态。

降级：重新录音；仍失败则标记 uncertain，不猜文本。

### 15.3 Acoustic Analysis

输入：音频及必要 alignment。

输出：语速、响度、停顿、有效时长等 Metric。

降级：标记 invalid，并记录原因。

### 15.4 Exercise Analysis

输入：Exercise、ASR、Metric、提示使用、重试次数。

输出：结构化事实与 Observation。

### 15.5 Patient Feedback

输入：已确认的 Observation / Metric。

输出：短、具体、可行动的患者语言。

降级：规则模板。

### 15.6 Session Adaptation

只允许在当前 Session 内：

- 增加提示。
- 降低单题复杂度。
- 延长等待时间。
- 替换更熟悉场景。

不得永久修改 TrainingPlan。

### 15.7 Session Summary

输入：结构化训练事实。

输出：患者训练总结。

降级：模板总结。

### 15.8 Trend Explanation

输入：Trend Engine 输出。

输出：自然语言解释。

AI 不负责决定“数字是否真的变化”。

### 15.9 Attention Summary

触发由规则或患者行为产生，AI 只负责说明“为什么被触发”。

### 15.10 Stage Review Assistant

输入：Evidence Package。

输出分为：

- System Observation
- Recommendation

不得自动改变阶段。

### 15.11 Therapist Plan Assistant

输入：当前计划、阶段回顾、康复目标。

输出：候选修改方案。

只能“采用 / 修改后采用 / 不采用”。

### 15.12 Companion Agent

定位为呈现层人格，负责：

- 欢迎。
- 朗读。
- 提示。
- 鼓励。
- 反馈。
- 组间过渡。
- 总结。

更换陪伴者的 avatar / voice / wording style 不得改变医学逻辑。

## 16. LLM 技术红线

任何 LLM 输出不得直接覆盖事实层数据。

LLM 可以生成：

- observation
- recommendation
- summary
- exercise_content

LLM 不得直接修改或生成：

- metric 原始值
- assessment_score 正式值
- recorded_audio
- prompt_usage
- completion_status
- 正式 TrainingPlan 生效版本

## 18. 产品成功标准

患者打开首页 5 秒内能够回答：

> 我今天要练什么？为什么？从哪里开始？

患者完成训练后能够回答：

> 今天哪里做得好？下一次继续练什么？

患者训练一段时间后能够回答：

> 我最近有没有变化？有哪些以前做不到、现在能做到的事情？

治疗师打开工作台 10 秒内能够回答：

> 今天哪些患者值得关注？为什么？

治疗师进入患者详情后能够回答：

> 最近发生了什么变化？证据是什么？我是否需要调整计划？

治疗师修改计划后，患者下一次训练必须真实发生变化。

## 19. 新版重构原则

新版开发采用 **Product Reset，不做 Code Reset**。

- 当前旧网页冻结为技术验证版本。
- 新前端与信息架构可以大幅重做。
- 后端已有认证、数据库、音频、ASR/provider、Assessment、comparability、临床审计等能力优先复用。
- 不能因为旧后端字段结构而倒逼新 UI。
- 必要时通过 adapter、新 endpoint 或模型重构支撑产品需求。
- 在产品规格未明确前，不允许 Codex 自行新增一级页面、导航或产品概念。
