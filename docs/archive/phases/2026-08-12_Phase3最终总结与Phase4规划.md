# 2026-08-12 Phase 3 最终总结与 Phase 4 规划

## 一、Phase 3 最终结论

Phase 3 的最终目标不是把系统做成复杂的治疗师审批后台，而是把 MVP 从“患者单端训练工具”推进到“三端分工清晰的康复协作系统”。

经过中途纠偏后，当前产品边界确定为：

```text
患者端：完成训练，理解反馈，看到简单进步。
家属端：看懂水平和趋势，获得陪伴建议。
治疗师端：查看训练记录和趋势，必要时用自然语言干预推荐方向。
算法层：负责能力画像、推荐生成、趋势归因和后续自适应策略。
```

其中最重要的产品判断是：

```text
训练推荐主路径应由算法支撑，不应依赖治疗师逐条复核。
```

治疗师可以观察、解释和干预，但不应该成为每次推荐的必经审批节点。

## 二、Phase 3 已完成能力

### 1. 报告系统重构

Phase 3.1 将早期“报告”从专业量表堆叠，调整为患者能理解的训练总结。

当前患者端报告重点展示：

- 已完成训练次数。
- 过程性表现摘要。
- 阶段变化说明。
- 下一步训练建议。

### 2. 患者端康复记录纠偏

Phase 3.2 明确患者端不展示治疗师级量表录入。

患者端康复记录当前只展示：

- 最近训练小结。
- 最近表现。
- 简化后的阶段记录。
- 面向患者和家属的自然语言说明。

### 3. 角色边界与路由骨架

Phase 3.3 建立三端路由与权限边界：

- 患者端：`/home`、`/training`、`/report`、`/ability` 等。
- 家属端：`/family`。
- 治疗师端：`/therapist`、`/therapist/assessments`、`/therapist/profiles`。

账号角色包括：

```text
patient
family
therapist
admin
```

### 4. 自动评估记录与治疗师复核

Phase 3.4 将“阶段评估”从手动录入为主，纠偏为：

```text
患者完成训练
-> 系统根据过程指标自动生成评估记录
-> 治疗师可复核或修正
```

该能力用于严肃评估记录，不等同于每次训练推荐都要人工审批。

### 5. 能力画像 MVP

Phase 3.5 建立能力画像：

- 当前内容难度。
- 当前自主程度。
- 近期过程指标均值。
- 画像摘要。
- 下一步建议。
- 置信度。

能力画像作为算法推荐的基础输入。

### 6. 画像驱动训练推荐

Phase 3.6 建立系统推荐能力：

- 根据能力画像生成推荐训练类型。
- 生成推荐标题、原因、关注点和建议时长。
- 患者端可从“按建议开始”进入训练。

当前推荐主路径已调整为：

```text
能力画像 -> 算法生成推荐 -> 患者端展示 -> 患者训练
```

治疗师自然语言说明会作为补充备注进入推荐结果，但不覆盖算法推荐主体。

### 7. 治疗师端三模块重构

Phase 3 后半段曾短暂走向“治疗师复核推荐与复杂调参入口”，后来确认方向偏重，已纠偏。

治疗师端最终收敛为三个模块：

1. 查看患者每次训练记录和评分结果。
2. 查看训练得分趋势：上次、三天内、七天内、三十天内。
3. 可选地用自然语言调整推荐训练内容。

对应新增接口：

```text
GET  /api/therapist/patients/{patient_user_id}/training-records
GET  /api/therapist/patients/{patient_user_id}/training-trends
GET  /api/therapist/patients/{patient_user_id}/recommendation-note
POST /api/therapist/patients/{patient_user_id}/recommendation-note
```

### 8. 家属端可视化观察面板

家属端不应像患者端一样过于简略，也不应像治疗师端一样专业密集。

当前家属端定位为：

```text
专业度介于患者端和治疗师端之间。
```

家属端已升级为图标可视化看板：

- 当前患者。
- 总体进度环。
- 训练坚持次数。
- 表达完整度。
- 稳定度。
- 说话节奏。
- 声音状态。
- 最近几次趋势柱状条。
- 系统/治疗师陪伴建议。

后端 `/api/family/observation` 已扩展返回可视化字段：

```text
current_level_label
progress_label
progress_percent
level_items
trend_items
```

## 三、当前三端职责边界

### 患者端

患者端负责：

- 创建和使用陪伴智能体。
- 进入训练。
- 完成录音。
- 查看即时反馈。
- 查看简单康复记录和能力画像说明。
- 按系统推荐继续训练。

患者端不负责：

- 理解专业量表。
- 录入阶段评估。
- 修改推荐策略。
- 查看治疗师级趋势分析。

### 家属端

家属端负责：

- 看患者是否坚持训练。
- 看当前水平大致处于什么状态。
- 看最近趋势是在进步、波动还是需要继续观察。
- 理解系统或治疗师给出的陪伴建议。

家属端不负责：

- 录入量表。
- 复核评估。
- 修改训练推荐。
- 查看过细的过程指标明细。

### 治疗师端

治疗师端负责：

- 查看患者训练记录。
- 查看每次训练评分结果。
- 查看上次、三天、七天、三十天趋势。
- 复核自动阶段评估。
- 必要时用自然语言补充推荐训练方向。

治疗师端不再作为：

- 每次训练推荐的审批后台。
- 复杂推荐策略调参中心。
- 必须手动录入所有评估结果的入口。

## 四、当前保留但降级的历史能力

Phase 3 中曾实现过一些偏重的能力，包括：

- `training_recommendation_reviews`
- 推荐复核接口。
- 推荐效果策略反馈接口。
- `recommendation_strategy_feedbacks`

当前处理方式：

- 数据表和旧接口暂时保留，避免破坏历史数据和兼容性。
- 前端主入口已不再使用复杂推荐复核流。
- 自然语言调整复用 `recommendation_strategy_feedbacks`，以 `manual_note` 标记。
- Phase 4.7 已将旧推荐复核和旧策略反馈接口标记为 deprecated。

## 五、当前推荐闭环

纠偏后的推荐闭环为：

```text
患者训练
-> 系统生成过程评分
-> 自动形成阶段评估记录
-> 能力画像刷新
-> 算法生成训练推荐
-> 患者按推荐训练
-> 治疗师查看训练记录和趋势
-> 治疗师必要时写自然语言调整说明
-> 家属端查看水平、趋势和陪伴建议
```

这个闭环的关键区别是：

```text
治疗师参与解释和干预，但不阻塞算法推荐运行。
```

## 七、Phase 4 总体方向

Phase 4 不建议继续在 Phase 3 的页面上堆新入口。

Phase 4 应进入：

```text
真实绑定、真实评估、真实内容、真实自适应。
```

## 八、Phase 4 建议拆分

### Phase 4.1 家属-患者正式绑定

目标：

- 替代当前“家属端默认查看第一个患者”的演示逻辑。
- 建立真实家属可见范围。

建议实现：

- 新增家属-患者绑定表。
- 支持一个患者绑定多个家属。
- 支持一个家属查看多个绑定患者。
- 家属端增加患者切换入口。
- 后端 family 接口只返回绑定患者数据。

验收标准：

- 未绑定家属看不到患者数据。
- 家属只能查看自己绑定的患者。
- 家属端可在多个绑定患者之间切换。

### Phase 4.2 训练内容库扩展

目标：

- 从少量 seed task 扩展到可支撑真实训练的内容库。

建议实现：

- 扩展短句跟读内容。
- 扩展场景表达内容。
- 引入内容难度分层。
- 引入自主程度分层。
- 支持治疗师创建或编辑训练材料。

验收标准：

- 每个训练类型至少有多组可选模板。
- 推荐系统能根据画像匹配不同难度内容。
- 治疗师可管理训练内容，但患者端仍只看到简单任务。

### Phase 4.3 推荐策略配置化

目标：

- 将当前硬编码推荐规则逐步配置化。

建议实现：

- 抽出推荐阈值配置。
- 支持按患者设置个体化偏好。
- 支持按治疗师建议写入算法参考条件。
- 保留算法自动推荐为主路径。

注意：

治疗师不直接拖拽调参，也不审批每条推荐。治疗师仍通过自然语言或有限配置影响推荐策略。

验收标准：

- 推荐规则不再完全写死在服务函数中。
- 能记录配置来源和更新时间。
- 患者端推荐结果仍保持简单。

### Phase 4.4 真实语音评估接入

目标：

- 从 Mock ASR / Mock 声学分析过渡到真实语音处理能力。

建议实现：

- 接入真实 ASR。
- 接入基础声学指标分析。
- 增加音频质量检测。
- 对失败、低质量音频给出可理解提示。
- 保留 mock provider 作为开发环境 fallback。

验收标准：

- 一次患者录音能产生真实转写文本。
- 系统能识别明显低质量录音。
- 过程指标来源可追踪。

### Phase 4.5 趋势归因与提醒

目标：

- 不只显示“变好/变差”，还要解释可能原因。

建议实现：

- 对比最近一次与三天、七天、三十天窗口。
- 区分训练不足、音量波动、语速波动、错误增加等原因。
- 患者端给一句简单建议。
- 家属端给陪伴建议。
- 治疗师端给更完整的趋势原因。

验收标准：

- 三端看到同一趋势的不同表达版本。
- 趋势解释不互相矛盾。
- 治疗师端可看到证据，患者端和家属端不暴露过度专业细节。

### Phase 4.6 自适应推荐增强

目标：

- 让推荐能根据历史效果逐步调整，而不是只看当前画像。

建议实现：

- 记录每次推荐后的训练结果。
- 建立推荐效果评分。
- 对连续有效的方向增加权重。
- 对连续无效的方向降级或切换。
- 将治疗师自然语言备注转成可供算法参考的约束。

验收标准：

- 同一患者连续训练后，推荐能随表现变化。
- 推荐变化有可解释依据。
- 治疗师可以看到推荐为什么变化。

### Phase 4.7 数据清理与旧接口退役

目标：

- 清理 Phase 3 走偏时留下但不再作为主路径的能力。

已完成处理：

- 旧推荐复核接口已标记为 deprecated。
- 旧策略反馈接口已标记为 deprecated。
- `training_recommendation_reviews` 与 `recommendation_strategy_feedbacks` 暂保留，作为历史数据兼容表。
- 前端主界面继续使用 `recommendation-note`、训练记录、训练趋势和推荐效果归因。
- API 文档已明确 deprecated 接口不属于当前主路径。

验收标准：

- 新开发者不会误以为治疗师复核推荐是主流程。
- API 文档与当前产品边界一致。
- 旧数据有迁移或兼容方案。

## 九、Phase 4 推荐优先级

建议优先顺序：

```text
P0：Phase 4.1 家属-患者正式绑定
P0：Phase 4.2 训练内容库扩展
P1：Phase 4.4 真实语音评估接入
P1：Phase 4.5 趋势归因与提醒
P2：Phase 4.3 推荐策略配置化
P2：Phase 4.6 自适应推荐增强
P2：Phase 4.7 旧接口退役
```

原因：

- 没有正式绑定，家属端仍是演示态。
- 没有内容库，推荐再聪明也没有足够训练材料可选。
- 没有真实语音评估，算法画像和趋势只能停留在 MVP 层。

## 十、Phase 3 收口判断

Phase 3 当前可以收口。

后续不建议继续在 Phase 3 内增加大功能。下一步应开启 Phase 4，并优先解决真实绑定与训练内容库。
