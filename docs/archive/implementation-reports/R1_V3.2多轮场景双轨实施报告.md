# R1 V3.2 多轮场景双轨实施报告

## 本轮范围与实际结构

完成态 `ScenarioDialogueSession` 现在可在旧场景评价成功后，影子写入既有
`evaluation_runs` / `evaluation_dimension_results`。写入使用固定算法版本
`functional-communication-eval-v3.0`、domain `functional_communication`、source
`dialogue_session`；未建立新的画像、策略或患者端 V3 展示。

六个维度为 `goal_achievement`、`information_sufficiency`、`response_ability`、
`relevance_and_organization`、`independence`、`repair_ability`。没有 overall
字段，也没有复用跟读对齐、发音或 dBFS 字段。`response_ability` 保存 agent
提问机会数及其后是否有患者回答；`relevance_and_organization` 保存患者 turn 数
和有可定位语义证据的 turn 数，二者不是同一 evidence snapshot。没有修复机会时
`repair_ability` 为 `not_observed` 且 value 为 null。

输入快照保存对话/任务/训练会话 ID、合同及版本、评估角色、全量有序 turn、
患者原话、ASR 和 LLM/provider/model/prompt 元数据、语义证据、提示事件和
对话状态。fingerprint 对算法版本、合同、turn 快照和人工覆盖内容稳定哈希，
同一输入重试复用已有 run。

## 安全门控与双轨边界

正式结果只接受 completed 会话、有患者表达、有 contract version、可定位到患者
原话的 `llm_structured` 引用、满足现有 R0 配置中工程质量下限的证据，并拒绝
`mock`、`fallback`、`unknown` ASR/provider 标记。fallback 语义、不可定位引用、
低质量证据或非完成会话不能成为 formal；空/终止会话为 unscorable。generalization
probe 永远 profile ineligible。这里的工程质量值来自 R0 版本化配置，非临床阈值。

旧 `ScenarioDialogueEvaluation` 和旧 API 保持不变；影子写入在旧结果已提交后
执行，任何 V3 失败均 rollback 自己的事务，不改变旧分数、趋势、训练或推荐。
V3 本轮没有被旧画像或 phase4.3 消费，也没有解除 R0 的 dBFS 或 phase4.3 冻结。

## 专业接口、复核、幂等与状态机

新增专业读取 `GET /api/scenario-dialogues/{dialogue_session_id}/evaluation-v3`，
以及 `POST /api/evaluation-runs/{run_id}/reviews`、`/recompute`。三者均要求治疗师/
管理员和患者归属权限。无影子 run 明确返回 404，不会临时计算患者端结果。

candidate 由已有 canonical service 采用；采用时旧 adopted 变 superseded，新的
run 关联 supersedes，数据库部分唯一索引与 PostgreSQL advisory lock 防止同一
source/domain 双 adopted。confirmed 仅追加 immutable revision，不创建 run。
corrected 会按被指定维度创建新 immutable run 并 supersede 旧 adopted；
unjudgeable 会将被指定维度写为 `unavailable/null`，绝不写为 0。新 candidate、
revision（带 recomputed run ID）与 adopted 切换在一个外层事务中提交；任何创建
candidate、追加 revision 或采用异常均 rollback 全部变更。revision 不会覆盖自动值。

每个复核请求由 server 根据 run、治疗师、action、目标维度和规范化复核 payload
生成 `review_request_key`（客户端也可提供同格式稳定键）。该键在同一 run 唯一；
重试返回已有 revision/recomputed run，不再新增 revision 或 adopted run。

## 持久化 retry 状态

新增通用 `evaluation_write_failures`（migration `0029_eval_write_retry`），供跟读与
场景影子写入共用。它保存 source type/id、domain、算法版本、输入 fingerprint（若
输入构建失败则使用稳定的 input-unavailable fingerprint）、failure stage、安全的
error code、retry required/count、失败/重试时间与 resolved run ID；不保存原始异常或
患者原文。任一后续同 source/domain/algorithm 写入成功都会将未解决记录设为
`retry_required=false` 并填写 `resolved_run_id`。旧训练结果已经提交后才记录失败，
所以 V3 写入故障不影响旧场景或跟读结果。
