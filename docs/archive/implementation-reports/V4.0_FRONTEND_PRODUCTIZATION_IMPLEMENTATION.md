# V4.0 Frontend Productization & Integration

## Architecture

V4.0 extends the existing Vue 3 single-page application instead of replacing it. Domain pages call typed clients in `frontend/src/api`; clients use the shared Axios envelope/error adapter; views do not call `fetch` or Axios directly. Existing patient training, legacy assessment, phase4.3, scoring, family, avatar, and provider-status flows remain in place.

Server state is loaded on route entry and refreshed only after a confirmed mutation. High-risk operations never run on page load. Profile rebuild, dataset freeze, controlled approval/apply/rollback, calibration, validation, and governance runs require explicit user action.

## Frontend stack

- Vue 3, Vue Router, Pinia, TypeScript, Vite
- Existing ECharts and Lucide packages remain available
- Axios shared client with typed `ApiError`
- Vitest, Vue Test Utils, and jsdom for unit/component/integration tests

## Route map

### Patient

- `/home` — current plan, current companion, patient-safe Profile summary
- `/training` and `/training/:type` — preserved repeat/scenario training flow
- `/evaluation`, `/report` — existing progress/history views
- `/patient/profile` — Profile V2 patient-safe projection
- `/ability` — retained legacy ability-profile compatibility route

### Therapist

- `/therapist` — quality and assigned-patient work overview
- `/therapist/patients` — searchable/filterable assigned-patient list
- `/therapist/patients/:patientId/:tab` — deep-linkable patient workspace
  - `overview`, `training`, `assessment`, `clinical-stage`, `profile`, `policy`, `controlled-actions`
- `/therapist/assessments` — existing assessment create/review workflow
- `/therapist/calibration`, `/therapist/policy-validation`, `/therapist/governance` — retained legacy deep links that redirect to the therapist dashboard; internal engineering workflows are not part of the normal therapist product navigation
- `/therapist/status` — existing system/provider status
- `/therapist/profiles` — retained legacy professional workspace compatibility route

## Role permissions

Route metadata keeps patient, family and therapist surfaces separate. Admin retains the existing therapist-view allowance. A patient route guard redirects professional routes to `/home`; a therapist attempting a patient-owned route is redirected to `/therapist`. Backend authorization remains authoritative for every read and mutation. A 403 does not remove the session; a 401 clears the token and returns to login.

## Patient experience

The existing login, repeat training, scenario training, recording, playback, submit, result, retry, avatar, and report components are preserved. Home now includes a patient-safe Profile summary. `/patient/profile` consumes only `GET /api/patient/profile`, shows dimension state/trend/evidence in natural language, and deliberately excludes raw values, provider metadata, reason codes, Policy and Governance.

## Therapist workspace

The patient list uses the real assignment-scoped patient endpoint and supports client-side search/status filters. The patient workspace combines real training records, assessment history, Clinical Stage, Profile V2, Policy V2 and controlled-action data under stable URLs and breadcrumbs.

## Clinical Stage

Clinical Stage detail, canonical preview, allowed source metadata update, and pairwise comparison use the existing therapist endpoints. Preview is visibly non-persistent. HTTP 409 responses are retained as business conflicts; finalized source-update conflicts receive a Review-flow explanation. Canonical and comparability values are rendered exactly as returned; the frontend does not recompute them.

## Calibration / Policy Validation / Governance

These internal engineering workflows are deliberately withheld from the therapist product shell. They require dataset, sample, decision, and proposal identifiers that are not clinician-facing concepts. Existing backend capability and frontend clients remain available for controlled internal use, but normal UI navigation and direct legacy URLs no longer expose raw-ID forms.

### Historical implementation note

The workspace supports dataset creation, ID-based detail loading, sample add/remove, freeze confirmation, independent annotation, adjudication, explicit calibration run, structured report display, and metric registry lookup. Frozen datasets disable editing. The backend currently has no dataset-list or metric-list endpoint, so the UI does not invent list data and uses known IDs/codes.

## Profile V2

Therapists can load the latest immutable snapshot, history, evidence links by dimension, freshness/status, versions and limitations, and explicitly rebuild after confirmation. The rebuild result is reloaded from the server. Patients receive only the safe projection.

## Policy V2

Latest and historical decisions, deterministic explanation, human-readable plus raw reason codes, append-only therapist feedback, and actual-training observation are integrated. Every professional Policy panel prominently labels `SHADOW` and states that it does not automatically change training. No patient/family route imports Policy APIs.

### Policy Validation historical note

The workspace creates a validation dataset, adds decisions, confirms freeze, runs validation explicitly, displays the returned structured report, and reads the registry. The backend currently has no validation-dataset read/list or remove-decision endpoint, so those controls cannot be truthfully implemented without a backend contract extension.

## Controlled Activation

The patient workspace supports proposal creation for the only two backend action types, detail-by-list display, approval, rejection, explicit apply, execution observation, rollback by execution ID, conflict messaging, suspended-state blocking, and history analytics. Apply is absent before approval. Approval copy explicitly says a separate Apply is required. Apply and rollback require second confirmation and wait for backend success before refreshing.

### Governance historical note

The workspace creates a governance dataset, adds proposal items, confirms freeze, runs all or one supported action type, displays the returned report, and reads the action-level registry. `manual_only`, `suspended`, and `eligible_for_streamlined_evaluation` use distinct text; streamlined eligibility explicitly does not imply automatic execution. The backend currently has no governance-dataset list/detail endpoint, so the workflow uses its returned dataset ID.

## API integration

New domain clients:

- `profileV2.ts`
- `clinicalStage.ts`
- `calibration.ts`
- `policyV2.ts`
- `policyValidation.ts`
- `controlledPolicy.ts`
- `governance.ts`

There are no mock-only product pages and no direct network calls in views/components. No V4 backend adapter or database migration was added. The API contract test verifies representative path/method pairs against the inspected router definitions.

## Error handling

The shared client translates 401, 403, 404, 409, 422 and 5xx responses while preserving backend detail. `ApiError` exposes status and detail for business-aware UI. Major pages provide loading, empty, error and success states. Mutations refresh state only after success; there is no fake optimistic completion.

## Accessibility

The V4 surface uses semantic headings, tables, labels, buttons and dialogs; visible focus rings; text plus tone for status; minimum touch sizes on small screens; reduced-motion handling; and scrollable tab/table containers. Patient language avoids diagnosis, deficiency and efficacy claims.

## Responsive design

Patient views collapse to a single column with larger controls below 640px. Professional two-column panels collapse on tablet, tables scroll horizontally, patient-workspace tabs remain usable as a horizontal list, and the sidebar navigation becomes scrollable rather than wrapping into an unreadable grid.

## Tests

Frontend tests cover status/reason vocabulary, common asynchronous states, patient-safe Profile empty state, patient/therapist route denial, controlled Apply gating and suspension, real API path/method contracts, and 409 preservation. The production build includes TypeScript checking.

## Known limitations

1. Calibration, Policy Validation and Governance lack backend list/detail contracts for some dataset entities. ID-based real workflows are implemented; no fake list is shown.
2. Policy Validation lacks a backend remove-decision endpoint, so frozen-state-safe removal cannot be offered.
3. Calibration annotation mutations intentionally do not reveal peer annotations; the current backend also has no adjudication-read endpoint, so the frontend cannot display Annotation A/B side-by-side.
4. Controlled proposal list payloads do not include an execution ID; rollback is therefore entered using the execution ID returned by Apply or audit context.
5. The current backend exposes structured dictionaries for several professional reports rather than stable response schemas. The frontend uses typed JSON objects and presents server fields without recomputation.
6. Vite reports existing large-bundle warnings. Route-level lazy loading is used for new pages; deeper vendor chunk tuning is deferred because it is not a functional blocker.
