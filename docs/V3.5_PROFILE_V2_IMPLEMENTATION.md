# V3.5 Profile V2 implementation report

## Scope and boundary

This delivery adds `profile-v2.0` as an immutable, shadow-only evidence projection. It does not alter `ability_profiles`, legacy patient scoring, patient training flow, phase4.3, or any recommendation/policy decision. The profile is an engineering evidence summary, not a clinical diagnosis, threshold, or treatment-effect claim.

## Data structure and migration

Migration `0033_profile_v2_snapshots` follows `0032_calibration_adjudication` and creates:

- `patient_profile_snapshots`: immutable version/config/fingerprint/payload snapshots with a previous-snapshot link;
- `profile_evidence_links`: queryable links from every adopted canonical V3 dimension to the snapshot, including source, run, provider/version, metric state, unit, review state, and clinical assessment reference;
- `profile_build_failures`: persistent, retryable build-failure state without raw exceptions.

All foreign keys use `RESTRICT`; old source records and canonical results are never changed or deleted by the builder. Snapshot idempotency is enforced by the database unique key `(patient_profile_id, evidence_fingerprint)`.

## Mapping, evidence policy, and aggregation

`app/modules/profile_v2/mapping.py` defines `profile-mapping-v1` and `profile-evidence-policy-v1`. It maps only existing V3.1 repeat, V3.2 functional communication, and V3.3 clinical-stage dimension codes. Each mapping records target code, source kind, direction semantics, aggregation and role eligibility, and mapping version.

Automatic dimensions require an adopted formal canonical run, a measured non-null value, and a `promoted` `MetricRegistry` entry. `experimental`, `shadow`, `suspended`, unknown, and provisional metrics do not enter the formal aggregate. Clinical manual dimensions remain independent of the automatic registry, but preserve assessment provenance and use the V3.3 comparability function before a clinical trend is shown. Unknown direction yields `mixed`, not an improvement/effect assertion.

Current state uses the configured latest-three-observation window, never an all-history mean. It groups by profile dimension, unit, and source kind, so manual and automatic evidence and differing units/scales cannot be silently flattened. The payload carries count, first/latest timestamps, trend/status, sufficiency, and limitations. No L/S field is created.

## APIs and authorization

- `GET /api/therapist/patients/{patient_user_id}/profile`
- `GET /api/therapist/patients/{patient_user_id}/profile/history`
- `GET /api/therapist/patients/{patient_user_id}/profile/{snapshot_id}/evidence`
- `POST /api/therapist/patients/{patient_user_id}/profile/rebuild`
- `GET /api/patient/profile` (patient-safe projection only)

Therapist endpoints reuse active therapist-patient assignment checks. The patient projection excludes raw values, provider metadata, and evidence links. `get_policy_profile()` is an internal deterministic reader that exposes only sufficient dimensions; it does not make a recommendation and is not consumed by legacy policy.

## Freshness, retry, and rebuild

Builds are explicit (`POST .../rebuild` or `python -m app.modules.profile_v2.run --patient <id>`), therefore they cannot block training, scoring, assessment, or shadow writes. A duplicate fingerprint returns the existing snapshot. Failures are persisted as a bounded error code/stage/retry state in `profile_build_failures`; a later successful identical rebuild resolves the row. `--all-stale` intentionally does not silently bulk-write: it is reserved for a scheduler/query integration after operational review.
